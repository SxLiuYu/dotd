## 二、四个缺陷（这两个 P0 最要紧）

### 2.1 定时任务从来建不出来（9.4）

**你看到的现象**：设了提醒，到点没反应。你可能以为是模型不行或者运气问题。

**真实原因**：`config/event-rules.yml` 里 `rules: []` 是空的（这是有意设计，
规则写错会误建任务），所以所有事件都交给模型判断「要不要建任务」。

对「外部来的、要不要处理得看内容」的事件（http/file）这是对的。
但定时任务是另一回事：它的 payload 里**已经带着** title 和 prompt，
「该不该建任务」在调度器那一步就答完了 —— 让模型重新判断一遍，本身就是错的。

而模型在实测中给出了两种都不是分类结果的回答：

```
prompt = "Reply with exactly: PROACTIVE-PROBE-OK"
模型回①  "PROACTIVE-PROBE-OK"           ← 它把数据当成指令执行了
模型回②  "I can't act on that message"  ← 强化 prompt 后转成过度防御
```

两种都让 `parseJsonOnce` 返回 null → 事件落 `inbox` → **任务永不创建**。
数据库里留着证据：事件 9 和 10 至今还是 `status='inbox'`，没有任何决策记录。

**修法**：`src/control-plane/match.ts` 新增 `heartbeatDecision()`，
定时任务事件**确定性短路**，直接按 payload 建任务（`via='rule'`, `confidence=1.0`）。
不再问模型。规则层仍然优先，你写规则可以覆盖。

**验证**：

- `tests/heartbeat-decision.test.ts` 18 断言全过。测试里的模型层故意设成
  **一调用就抛错**，所以它证明的不是「返回 null 也能过」，而是「根本走不到模型层」。
- 反向注入：删掉短路 → 立即 `Error: heartbeat 不该调模型层`，栈直指 `matchByLlm`。
- 端到端：`ct_a1v3` → `ev13 matched(via=rule)` → `tk_ev_13 done` →
  飞书实收 `PROACTIVE-PROBE-OK`（`surf_outbound_log` 808/809, `ok=1`）。

### 2.2 主动推送开关根本不生效（A1）

**这个比上一个更隐蔽**：三闸（开关/安静时段/节流）的计算是对的，
`shouldPush()` 在 `fireHeartbeat` 里正确算出了结论，写进 `events.payload.proactive` ——

**然后全仓没有任何地方读它。**

实测：建一条 `proactive=0` 和一条 `proactive=1`，同一时刻触发，**两条都推到了飞书**
（`surf_outbound_log` 811/812）。也就是说「主动推送开关」此前完全是摆设，
关着的任务照样每天打扰你 —— 而「关掉通知」是你唯一能做的反抗。

**修法**：`src/surfaces/feishu-outbound.ts` 新增 `shouldAnnounce(db, taskId)`，
在 `taskStateText` 里消费那个判定。**只读回调度器的结论，不重算** ——
重算会因为 `last_push_at` 已被更新而得出不同答案。

判据刻意收窄到**只有一种情况静默**：heartbeat 来源 + `payload.proactive === false`。
其余一律照常回：

- 没有 `source_event_id`（你在对话里说话）—— 回复是应答，不是打扰；
- 非 heartbeat 来源（http/file 等）；
- payload 缺 `proactive` 字段（老事件）—— 向后兼容优先；
- 事件行被清理了、JSON 坏了、task 查不到；
- `proactive` 不是严格布尔（比如字符串 `"false"` 或数字 `0`）。

最后这几条的共同原则：**宁可多说一句，也别吞掉你的回答**。

**验证**（同刻触发两条对照）：

```
ct_g2_on  (proactive=1) → tk_ev_16 done + 飞书收到 G2-ON
ct_g2_off (proactive=0) → tk_ev_17 done + 无出站记录
```

**注意**：两条任务都 `done`。这证明的是「不推送 ≠ 不干活」——
定时任务的价值常在副作用（写文件、更新记忆），静默不等于该跳过。

反向注入：删掉 `shouldAnnounce` 调用 → `ct_g3_off` 的 `G3-OFF` 又被推送（id 815），
原 bug 重现；恢复后重新对照，只有一条出站。

### 2.3 截图一张都没发出去过（第二轮发现）

**这个最难发现**，因为代码看着完全正确：读图、发图、去重三件齐备，47 条测试全过。

真跑一遍才发现：截图在容器里造得出来（67006 字节 PNG），**一张都没送到你手上**。
进度推了 7 次，日志里 7 行「推了进度」，**零行「随进度发了截图」** ——
也没有任何「读图失败」，因为发图函数压根没被调用。

根因：`steps.result_json` 里存的不是 `{path: ...}`，而是

```json
{"output":"{\"path\":\"/dot/home/screenshots/x.png\"}"}
```

工具输出先被字符串化、又包了一层。而解析函数只认前一种形状，于是永远返回 null，
附图分支静默跳过。

**为什么测试没抓到**：那 47 条测的是去重逻辑（`decideScreen`），输入是我手写的
路径字符串。真实的数据形状从没进过测试视野。这是「纯函数测对了，接线处形状错了」。

修好后日志变成 `随进度发了截图（67006B）`，出现 3 次。

**一个你可能关心的副作用**：正式节流是「每 3 步 + 至少隔 90 秒」。
一个 20 秒跑完的任务只会在第 1 步推一次，那时还没截图 ——
所以**短任务基本看不到过程图**，长任务才有。这是节流按设计工作，不是 bug。

### 2.4 进度推送「配了但从不生效」（第二轮发现）

打开 `progress.enabled` 的过程本身挖出一个缺陷。

`_config_src.yml` 里 `progress:` 的缩进是 6/8 空格（应为 2/4），被 YAML
解析成 `ui.stream_deltas` 的**子节点**。于是 `surfaces.progress` 恒为 `undefined`，
由 zod 的默认值兜底 —— 看起来配了，实际从没生效。而启动脚本每次都用这个文件
覆盖 `~/.dotd/config.yml`，谁改都会被冲掉。

修好后启动日志：`过程可视化已启用（每 3 步 / 至少隔 90 秒）`。

## 三、五个能力补齐

### 3.1 活动/回执总览（9.3）

**做了什么**：`GET /api/activity` + `dotd activity` 命令 + Web 活动视图。

回答的问题不同：

- `dotd task <id> --verbose` —— 这一个任务每一步如何（成本/耗时/瓶颈）；
- `dotd activity` —— 最近这一批任务各自结果如何。

与 `/api/queue` 的分工是 SQL 谓词上的互补：queue 只回非终态（在途），
activity 的主体恰恰是终态（已完成的）。

实测输出：

```
全部任务：完成 1264 · 取消 26 · paused 3

最近 3 个任务：
  10-21 17:30  完成    g3-off（2 步）
  10-21 17:30  完成    g3-on（2 步）
```

`limit` 三向夹逼实测：`999→100`、`abc→20`、`0→1`。
失败步数**只在真有时显示**（每行都写「失败 0」等于噪音）。

Web 侧新增 `ActivityView.tsx`，登记为第七个视图。刻意**不订阅 SSE** ——
活动是已经结束的事实，接实时流会让人误以为在看直播。
`npm --prefix web-ui run build` 通过（含 `tsc --noEmit`）。

### 3.2 审批金额显示（9.2）

**先说清楚我没做什么**：我**没有**实现「低于阈值自动放行」。

那会破坏「花钱一律要人批」这条硬边界（GOV §4.1/§4.5：spend 永不进记忆、永不自动）。
审批少一次和钱多扣一笔，代价不对称。

我实现的是**让你更容易看懂自己在批什么**：

- `amountCents` 全链语义是**分**，但卡片原来直接印 `12500 CNY` ——
  等于把 125 元显示成 12500 元。现在印 `CNY 125.00`。
- 零小数币种（JPY/KRW/VND/CLP/ISK/HUF）原样不换算。
- 超过 500 元加 `⚠️ 金额较大，请确认`。
- 裸 `amount` 字段（单位不明）标注「（未标明单位）」，不再假装知道是分还是元。

实测卡片文本：`· 金额：CNY 500.00  ⚠️ 金额较大，请确认`

顺带修了一个**测试本身是错的**的地方：`tests/approval-card.test.ts` 原来断言
`t.includes('50000')` —— 那个断言把「500 元显示成 50000 元」当成了正确行为。
已改为 `500.00 CNY`。

### 3.3 进度推送接截图（9.1）

把已有两个轮子接上：`browser.screenshot` 产出的 `imagePath` 现在会随进度推送发出。

去重逻辑抽成纯函数 `decideScreen(path, lastSentPath, needsAttention)`，三条规则：
无图不发、同上张不发、`needsAttention` 时不查重（该看的时候必须看到）。

顺序**固定为先文字后图片**：文字失败就不发图，避免你收到一张没有说明的截图。

### 3.4 金额阈值规则（9.5）—— 受限实现，原因要说清

清单原话是「加数值阈值规则（"超过 ¥500 才问"）」，**字面读 = 低于阈值不问**。

这条读法与项目自己的硬约束直接冲突：

- `docs/design/modules/governance.md:105`：`spend | approve | 一律人工审批`；
- `rules.yml` 只能收紧（降档在加载时拒绝并告警）。

`rules.yml` 的 `decision` 只有 `allow/review/approve/deny`，命中后只能升级不能降级。
所以「加个谓词就能免审批花钱」在本架构里**结构上做不到** —— 不是没实现，是设计上拒绝。

**我实现的是阈值的可用形式**：新增谓词 `match.amountAtLeast`（单位分）。

```yaml
rules:
  - match:
      tool: shop.checkout
      amountAtLeast: 50000        # ≥ ¥500
    decision: approve
    reason: "单笔 500 元以上必须人工确认"
```

因为命中后只能转 `approve`/`deny`，这个谓词**不可能**产生「低于阈值放行」。
写 `decision: allow` 配它会在加载时被拒：

```
试图把 approve 放宽为 allow，已拒绝
```

**当前限制**：阶段一 `config/tools.yml` **没有登记任何 spend 档工具**
（`shop.checkout` 是注释掉的结构示例）。所以这个谓词现在可用于 `fs.write` 等
收紧场景，真正用在花钱上要等阶段二接入支付类工具 —— **那时不用改代码，只加配置**。

### 3.5 真流式输出（B2）—— 早已实现，本轮只做确认

checklist 说「前端订阅了 `chat.delta` 但全仓库无生产者」。实测推翻：

`src/runner/dot.ts:1628` 的 `publishChatDelta()` 就是生产者。订阅 SSE 后发一条消息，
收到 **16 条 `chat.delta`**，内容是逐字增量（首条 delta 只有一个「你」字）。
真流式一直在工作。

## 四、哪些我做不到（需要你处理）

按「不该做」和「做不到」分开 —— 这是两种完全不同的东西。

### 4.0 清单：确实实现不了的（逐项对账）

| 项 | 类别 | 为什么 |
|---|---|---|
| **人格 / 情绪** | 技术上做不到 | 语言模型行为层面，应用层只能写 prompt 模仿，写不出真有情绪的系统 |
| **可爱形象**（外观/动作） | 做不到（本仓库范畴内） | 需要 3D 资产 + 渲染管线，与「本地 agent 运行时」是两类工程 |
| **硬件**（实体桌面机器人） | 做不到 | 需要机械/电子设计与制造，不是软件问题 |
| **打电话**（语音通话） | 做不到 | 需要 SIP/PSTN 线路 + 实时语音编解码 + 合规资质 |
| **原生 App**（iOS/Android） | 不该做（现阶段） | 技术上可行，但飞书卡片覆盖手机端、Web 覆盖桌面端，增量价值主要是推送到达率，而飞书已解决 |
| **Gmail OAuth** | 能做，卡外部凭据 | 需 Google 应用注册 + 审核 + token 加密存储，要你的账号授权 |
| **Stripe / 真支付** | 能做，卡外部凭据 | 需商户资质 + API key；且 spend 档一律人工审批是刻意设计 |
| **Google Calendar OAuth** | 能做，卡外部凭据 | 同 Gmail；现在 `calendar.*` 读写本地 `.ics` 已可用 |

前三项和「原生 App」的区别很重要：
- **做不到** = 不是软件能解决的事（人格在模型层，其余在物理世界）；
- **不该做** = 软件能做，但投入产出比现在不成立 —— 这是产品判断，你随时可以推翻。

### 4.1 技术上做不到（展开说人格这一项）

**Muse 的人格与情绪**。meta-muse 里那些「它会主动关心你」「它有情绪起伏」的描述，
不是功能清单，是语言模型行为层面的东西。我可以写 prompt 让它**模仿**关心，
但写不出一个「真的有情绪」的系统 —— 那需要在模型层解决，不在应用层。

如果你要的是「感觉像 Muse」，可以调 persona prompt + 记忆注入 +
主动发起对话频率。这是**逼近**，不是**实现**。要不要做这个逼近，是产品决定，等你定。

### 4.2 该不该做（能实现，但我不建议现在做）

**原生 App（iOS/Android）**。技术上完全可行。但不建议：

- 飞书卡片已经覆盖「在手机上看结果、点审批」；
- Web UI 覆盖「在电脑上细看」；
- 原生 App 的增量价值主要是推送到达率，而飞书已经解决了。

真要做，那是独立项目，不是「对齐 Muse」的一部分。

**外部账号集成（IMAP/日历同步）**。当前状态：

- 邮件：已注册 8 个工具，能读写本地邮件目录；
- 日历：已注册 5 个工具（读 2 + 写 3），写只动本地 `.ics`。

缺的是**双向同步**（连你的 Gmail/Outlook）。这需要 OAuth 应用注册、token 刷新、
增量同步协议 —— 工程量是当前的数倍，且要你的账号授权。**需要你决定要不要投入**。

### 4.3 我没验的（可能是坑）

诚实列出来，不装作都验过：

- **真人收到推送的观感**。我验的是「发出去了」（`ok=1`），没验「看起来对不对」。
- **「早间日程提醒」明天 9:00 真会推**。我把它 `proactive` 打开了（节流 20 小时），
  三道闸已逐条实测（见 `muse-parity.md` §3.2），但**没等到它自然触发**。
  明天早上是第一次真实检验。**这是本轮唯一真正待验的事。**
- **长任务的过程截图观感**。链路已实测（67006B 真的发出去了），但正式节流是
  「每 3 步 + 90 秒」，我只在把阈值临时调到 1/0 时验过连续推送。
  真实长任务下你多久能看到一张图，没验。
- **跨网络稳定性**。飞书长连接在断网重连时的行为，没压测。
- **Muse 的记忆/并行/重试机制**。见 `docs/meta-muse.md` §8，那里标的是未验。

## 六、下一轮建议

按价值排序（不是按工作量）：

1. **明早验证「早间日程提醒」是否真推送**。这是本轮改动唯一的真实场景检验，
   链路已经打通，但得等到自然触发才知道成不成。
2. **`event-rules.yml` 是否要加规则**。现在默认空 = 全走模型层，
   对 http/file 类事件意味着每次都要一次 LLM 调用（延迟 1–15s）。
   如果你有固定的自动化来源（比如 GitHub webhook），写规则会快很多也稳很多。
3. **外部账号集成**要不要做 —— 这个要你先定，因为工作量和授权都在你那边。
