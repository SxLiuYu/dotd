## 已搭好的观测设施（真跑 7 天所需的一切就绪）

### 1. `scripts/soak.sh` —— 长期采样 + 真实业务探针
```
*/30 * * * *  /root/dotd/scripts/soak.sh sample   # 每 30 分钟采一次
0 */6 * * *   /root/dotd/scripts/soak.sh probe    # 每 6 小时跑一次真任务
```
- `sample` 记录：时间戳、daemon 是否存活、**RSS**、**fd 句柄数**、线程数、
  容器是否 Up、DB 大小 → `docs/acceptance/soak.jsonl`
- `probe` **不是端口探测**：它真的提交一条消息、等它 `done`，记录成功/失败与耗时。
  端口通但模型挂了这种情况，只有这样才测得出来。
- `report` 读 jsonl 算：已跑天数、RSS 增长/峰值、句柄增长/峰值、探针成功率，
  逐条对照判据给出结论。

已装进 crontab（`bash scripts/soak.sh install_cron`），当前 `crontab -l` 可见两条。

**采样器刻意不修任何东西**：一旦它去"修理"，测的就不是长期稳定性了。

### 2. `scripts/soak-stress.sh` —— 加速耐久（早期信号，非判据）
用高密度真实任务在几十分钟内压出趋势。40 个混合任务（算数/读文件/出网/
写文件/读 PDF/复用工具/定时）实测：

```
起点 RSS=186MB fd=26   19:29:58
[10/40] pass=10 fail=0  RSS=191MB fd=28
[20/40] pass=20 fail=0  RSS=195MB fd=28
[30/40] pass=30 fail=0  RSS=198MB fd=28
[40/40] pass=40 fail=0  RSS=200MB fd=29

任务：40 成功 / 0 失败  成功率 100%
RSS：186MB → 200MB，增长 14MB
句柄：26 → 29，增长 3
```

读法：RSS 前 10 个任务涨 5MB，之后每 10 个只涨 3–4MB，**增速在收敛不是线性泄漏**；
句柄 26→28 后一直卡在 28，跑到 40 个才 +1，符合"缓存的连接池到顶"而非"每次泄漏一个"。
这是**正面信号**，但**不能**据此宣布 7 天达标——真正的泄漏可能几十小时后才显形。

## 第 3 轮：把"观测器本身"修到可信

这一路反复验证了同一件事：**判据本身也会说谎**。本轮又抓到五处，都已修并有反向验证。

| # | 原来的谎 | 后果 | 修法 |
|---|---|---|---|
| 1 | 探测只发"回复 OK 两个字母就行" | 只能证明进程活着，证明不了"成功率不掉" | 轮换 4 类真实任务（存活/推理/读文件+工具/容器执行）并**核对答案** |
| 2 | 轮换用 `date +%H % 4`，而 cron 是 `0 */6 * * *` | `%H%4` 只可能 0/2，**slot 1、3 永远轮不到**，一半能力没测过 | 改用"已有 probe 记录数"当指针，与触发时刻无关 |
| 3 | `$(grep -c … 2>/dev/null \|\| echo 0)` | `grep -c` 空匹配时**既返回 1 又打印 0** → 拼出 `"0\n0"` → `$(( ))` 语法错误 | `grep -c … \| head -1` 再兜底；边界已验 |
| 4 | `proc_start=$(stat -c %Y /proc/$pid)` | 取的是**目录 mtime**，进程新增 fd 就变 → **同一 daemon 被算成 2 次重启**，还凭空报"疑似人工干预" | `btime + /proc/<pid>/stat` 第 22 字段；算出值与 `ps -o lstart` 一致且稳定 |
| 5 | RSS/句柄用**单点首尾差** | 高峰落在末点 → 误判泄漏（本轮真踩到）；落在首点 → **掩盖**真泄漏 | 取首/末段各 10% 样本的**中位数**比较 |

第 5 条的验证是双向的，这才说明它没被改松：

- 尖峰在末尾 → 200.0→200.0（+0.0MB）通过 ← 旧逻辑会误判泄漏
- 尖峰在开头 → 200.0→200.0（+0.0MB）通过 ← 旧逻辑会掩盖
- **真实泄漏 +60MB** → 首段 202.9 → 末段 257.1（+54.2MB）→ ❌ exit 1
- **真实 fd 泄漏 +5** → 句柄 34→39 → ❌ exit 1
- 健康 +10MB → +9.0MB → ✅ exit 0

**关键是"没翻倍"**：任务数翻倍，RSS 增长没有跟着翻倍 → 是 GC 波动，不是泄漏。
累计跑到 930 个任务时 RSS 仍为 222MB、fd 回落到 34，进一步支持这个判断。
若真按"每任务线性涨"外推，60 个任务就该涨 16MB、500 个任务就破 50MB —— 实测没有。

但这**仍不能替代 7 天**：内存碎片、低频路径上的句柄累积，都可能在长尺度才显形。

## 归因：区分"自愈"和"人工"

S6 的字面要求是"无**人工**干预"。原报告只说"期间重启过 N 次"，不区分这两者，
而它们性质相反：watchdog 自愈恰恰是长期运行该有的能力，人工重启才会让窗口作废。
现在每次重启都回 watchdog 日志找证据（新进程起来前 15 分钟内有"自愈:…已恢复"→ 判自愈），
找不到就如实标成"无自愈记录（疑似人工干预）"，并把 exit 置 1。
