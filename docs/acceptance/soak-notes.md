# S6 窗口旁注：过程中发生过什么

这份文件记录**窗口期间对数据产生过影响的事件**。
`soak.jsonl` 只存事实，不存原因；原因记在这里。

---

## 2026-10-20 11:18:00 —— 一条非 cron 采样的来历（第 108 轮自己造成的）

**发生了什么**：我用 `env -i PATH=... bash /root/dotd/scripts/soak.sh` 去验证
「cron 的最小环境能不能跑通它」——以为不带参数会打印用法，
结果 `soak.sh:2467` 是 `case "${1:-sample}"`，**不带参数 = 执行 `sample`**。
于是真的往窗口里写了一条采样点。

**数据点**：
```json
{"ts":1792466280,"alive":true,"rss_kb":220720,"fd":27,"threads":11,
 "container_up":1,"db_kb":18860,"pid":196833,"container_start":1792437900,...}
```
`ts=1792466280` = `2026-10-20 11:18:00`，`rss=215.5MB`。

**为什么不删掉它**：
1. 它是真的从真 daemon 采样出来的，`215.5MB` 是那一刻的真实值；
2. 删它就是篡改证据 —— 哪怕它是我自己造成的。
   我在 R104 刚因为「拿没中断保护的设计去碰正在计时的窗口」写过检讨，
   这次至少不应该再靠删数据把现场打扫干净；
3. 影响可量化且远未触及门槛（见下）。

**对判据的实际影响**（实测前后对比）：

| 判据 | 有这条 | 去掉这条 | 门槛 |
|---|---|---|---|
| 采样密度 | 120% | 109% | ≥70%，且 ≤150% |
| 全窗口 RSS 峰值增长 | +6.7MB | +5.0MB | <50MB |
| RSS 首段中位 | 210.6MB | 210.1MB | — |

也就是说：**它让密度虚高 11 个百分点、让 RSS 峰值虚高 1.7MB**，两条判据都远在门槛内。

**真正该修的是设计**：`case "${1:-sample}"` 让「误敲」等于「写数据」。
正确的大概应该是 `case "${1:-usage}"`，无参数打印用法并 `exit 1`。
但这要动 `soak.sh`（当前 md5 `98824045`，窗口期间冻结），已记 `docs/backlog.md`。

**在冻结期内怎么防再犯**：见下一个文件 `docs/acceptance/NO-ARG-TRAP.md`。

## 规矩

以后窗口期间发生任何「非 cron 产生」的数据写入，都要在这里记一条：
时间 / 什么操作 / 哪些行 / 对判据的影响 / 为什么保留。
