- **实测**：

  - ✅ (c) 三工具六环齐（容器实现/能力目录/白名单/治理/说明书）
  - ✅ (b) **已达成（2026-10-19，端到端真链路）**：`scripts/s2-reuse.sh` 跑通 ——
    模型发 `word-count` → 被翻译成 `tool.invoke` → succeeded，工具数仍为 1（没重复造）
  - ✅ (b) **跨模型复验**：deepseek-v4.1-flash / glm-5.3-flash / agnes-3.0-flash
    三个厂商 **全部 PASS**（都只调 tool.invoke、无 shell.run）。这三个模型此前全部失败
- **关键根因与解法**（前一会话定位、本会话落地）：
  提示词试满 3 次全败；根因不是模型不听话，而是"自造工具只是注入文本里的数据"，
  模型要做"看到文字→想到 tool.invoke(name)"的间接映射，对三个厂商都超纲。
  正解是把自造工具**动态注册成独立 tool**（名字即工具名、带自己的 args_schema）。
  但只做暴露不做路由会更糟（模型照着调必然被 `unknown_tool`/`工具未登记` 拒），
  故补齐执行路由：派发口翻译成 `tool.invoke(name=<它>, args=<模型参数>)`。
- ✅ (b) **本会话用更严判据复验（2026-10-19）**：新增 `scripts/s2b-verify.sh`，
  不再"只要出现 tool.invoke 就算过"（那会漏掉"先 shell.run 手写一遍、失败才想到
  现成工具"和"invoke 完又用 shell.run 复核"），改要求**四条同时成立**：
  ① 有 tool.invoke；② **全程零 shell.run**；③ 工具数不变（没新建）；④ 任务 done 且有回答。
  连跑 **3 次全部 PASS**，每次工具序列都是 `[tool.invoke:succeeded]`、零 shell.run、工具数 2→2。
  答案数字也核对过：`Hello 世界，this is a test 测试。` = 27 字符 / 22 非空白 /
  4 汉字 / 16 字母，与容器内 `run.py` 直算结果逐一吻合（此前基准打印 0 是我的脚本
  取错字段 `chars`，实际字段是 `total_chars`，已修）。
- **结论**：✅ 通过（S2 三条判据全部达成，且 (b) 以更严判据复验 3/3）

## S5 故障自恢复
- **判据**：3 种故障（容器停 / 网关端口不可用 / daemon kill -9）→ 3/3 无人干预自愈，< 5 分钟
- **实测**：**3/3 = 100%**，容器 53s、relay 55s、daemon 115s，全部 < 300s
  （`docs/recovery-report.md` + `docs/acceptance/recovery.jsonl`）
- **结论**：✅ 通过
- **修掉三个真实缺陷**（原本这步过不去，不是判据太严，是系统真不会自愈）：
  ① **watchdog 没装进 cron** —— 脚本早写好也拷到 /usr/local/bin，但 crontab 里没有，
     从不执行；`docker stop` 后 5 分钟仍是 Exited。已装为 `*/2 * * * *`。
  ② **watchdog 只检测容器、没有修复容器的代码** —— 日志连续报
     `container 失败（第 1/2 次）` 却不动手，因为它只有 repair_daemon/docker/relay。
     已补 `repair_container`（先 docker start，失败退到 fleet 重建）并在检测失败时立即调用。
  ③ **cron 下找不到 powershell.exe → relay 永远修不好** —— cron 的 PATH 不含
     `/mnt/c/...` 互操作路径，脚本里 `command -v powershell.exe` 直接放弃自愈，
     只剩发告警。已在脚本开头显式补 PATH；用 `env -i PATH=/usr/bin:/bin` 模拟验证通过。
- **验收设计**：脚本**绝不修故障**（只造故障 + 干等），避免"测的是脚本"；
  恢复判据不是"端口通"，每条都补一次真实业务动作（执行命令 / 提交任务等 done）；
  并核对日志时刻对齐 cron 整分钟，确认恢复来自无人值守路径而非我手动跑。
