  提示词试满 3 次全败；根因不是模型不听话，而是"自造工具只是注入文本里的数据"，

  不再"只要出现 tool.invoke 就算过"（那会漏掉"先 shell.run 手写一遍、失败才想到
  现成工具"和"invoke 完又用 shell.run 复核"），改要求**四条同时成立**：
  ① 有 tool.invoke；② **全程零 shell.run**；③ 工具数不变（没新建）；④ 任务 done 且有回答。

      ② 连续 3 次失败 → `ready → unhealthy`；③ `periodicHealthCheck` 想恢复，
      **又用同一个旧 endpoint 探活** → 还是失败；④ `wakeForDispatch` 只认
      `suspended/idle/stopped/idle_stop_requested`，**`unhealthy` 不在名单** →
      永不唤醒。于是成了没有出口的闭环。
    - **这恰恰是 S6「连续 7 天无人工干预」的硬伤**：Docker 重排一次 IP 就永久
      报废容器能力，而判据只看到"进程没重启、没句柄泄漏、RSS 正常"，**一路绿灯**
      —— 直到成功率掉下来，那时 7 天已经白跑。**判据测的是"进程活着"，不是"能干活"。**
    - 修法 `fleet.resyncEndpointFromDocker`：探活失败时直接问 docker 要实况 ——
      原 id 还在就跑读它现在的 IP，原 id 不在就按 label `dotd.dot=<dotId>` 重新发现，
      容器真没了就如实返回 null（不许编一个地址）。只改记录，不重启容器。
    - **验证（新增 2 条测试，1579/1579 全绿）**：① IP 变了 → 能纠正并落库，
      且落库的 id 在 docker 实况里找得到；② 容器真没了 → 返回 null，不假装修好了。
    - **诊断的独立验证**：只改库里那一行（不动代码、不重启 daemon），
      **45 秒内 `unhealthy → ready`**，`periodicHealthCheck` 立刻自愈成功；
      随后 slot=2 / slot=3 从 `ok=false`（23s 失败）变成 **`ok=true`（6s / 10s）**。
      这证明系统本身的恢复逻辑是好的，只是被过期记录挡住了。
- **结论**：❌ 未通过。剩下 **1 条 ❌：未满 7 天**（5h/168h）。
  本轮修掉了一个**判据看不见的致命缺陷**（容器能力全废 5 小时而全绿），
  但修复要生效需重启 daemon → 窗口会重新计时。下一轮决策。
  `docs/soak-report.md` 如实记录，7 天后跑 `bash scripts/soak.sh report` 复判。
- **修掉采样器的一处"假数据"**（第 2 轮自查发现）：第一版 `report` 直接把最早与最晚样本的
  RSS 相减，得出"RSS 增长 **-32.1MB**"这种好看但无意义的数字 —— 期间 daemon 被重启过，
  拿新进程的小内存减旧进程的大内存，等于没测。已让 `sample` 记录 daemon 身份
  （`pid` + `proc_start`），`report` 改为**只在同一生命周期内**算增长，并显示"生命周期数"
  （>1 即说明期间重启过）。旧的无身份样本已移出 `soak.pre-fix.bak`，避免污染。
