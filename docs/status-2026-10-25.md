## 0. 一句话结论

**仓库是健康的，线上不是仓库。** `/root/dotd` 是一个非 git 的旧副本，落后仓库
18 个改动文件 + 7 个新文件，模型还停在更慢的 `deepseek-v4-1-flash-1017`。
所以 `12f9b42` 里那批延迟优化（补写轮闸门、guard 基线、proof 时间线）**线上一条都没生效**。

比延迟更严重的是能力性故障：**容器已被隔离 29 小时**，`shell.run`/`browser.*`
现在派发即失败；队列里还有 1 条交互任务卡了 48 小时、2 条任务因端点不可达暂停后
不会自动回队、1 条审批挂了 24 小时没提醒（根因是 `expirePending` **从来没被调度过**，
本次已修，见 §9）。

## 2. 模型：仓库里的选择是对的，线上是更慢的那个

同一提示、同批 3 次、带 tools 的 TTFT：

| 模型 id | p50 | min–max |
|---|---|---|

## 5. 现场问题（都有证据）

1. **容器隔离 29 小时**（最严重的能力性故障）。
   `GET /api/container` → `state=quarantined`、`recreateCount=5`、
   `lastHealthAt=2026-10-24T03:20:56Z`，提示"24 h 内重建超过 3 次"。
   现在任何 `shell.run` / `browser.*` 都会返回 `container_not_ready`。
   近 7 天 `shell.run` 的失败样例就是这个码。
2. **1 条交互任务卡在队列 48 小时**。
   `tk_mvk7kkrhi9muc2`，priority 1，2026-10-23 08:05 入队，`updated_at` 也是那一刻。
   当天 `watermark` 标定 `baseMb≈22.2 GB`（正是"p50 当 throttled 门槛"的 bug 现场），
   队列被水位钉住，任务再没被 pop。这就是 `12f9b42` 修掉的那个 bug 的受害者。
3. **2 条任务 `paused(endpoints_unreachable)` 不会自动回队**。
   一条 10-23 09:24 创建、11:22 暂停；另一条 10-25 00:15 创建、00:17 暂停。
   后者对应 `model_call_log` 里 00:16:00 / 00:16:59 / 00:17:58 连续三次 timeout
   （1017 → glm → minimax，间隔 59 s）。网关随后恢复，但任务没有恢复路径。
4. **1 条审批挂了 24 小时，且过期扫描根本没在跑**。
   `approvals#159`（task `tk_ev_34`，`shell.run` dangerous）创建于 10-24 08:30，
   `reminded_at` 为空（从未提醒），`pending_until=2026-10-25T08:37:23+08:00`。
   查代码发现根因：`expirePending`（`src/governance/gate.ts:1854`，注释写着
   "cron 每 5 分钟"）**在生产装配里没有任何调用点**——只有测试在调。
   所以到了 `pending_until` 也不会转 `expired`，宿主任务永远 `awaiting_approval`，
   `/api/status` 永远报 `approvalsPending=1`。
   **本次已修**：注册成 `gov.approval-expiry` 的 5 分钟 light job（见 §9）。
5. **孤儿步骤 26 条**：14 条 `started`（LLM 步，无 `finished_at`）、
   12 条 `pending`（`shell.run` 7、`tool.invoke` 2、`browser.*` 2、`tool.create` 1）。
   任务中断后没有收尾，后续统计（如"每任务耗时"）会被它们污染。
6. **工具失败率**：`web.read` 36%（22/61）、`net.get` 19%（43/230，其中一部分是
   `DOTD_NET_TOOLS=off` 的预期拒绝）、`browser.open` 19%（23/124）。
   `search.web` 有集成错误：`argo search 失败：usage: search.py [-h] ...`（调用参数不对）。
7. **watchdog 事件噪声**：7 天 711 条，其中 366 条 `{"shutdown_marker":true}`、
   345 条 `{"lastShutdown":"graceful"}`——每次启动写 1–2 条，约 350 次启动记录
   把日志刷满（集中在 10-19 ~ 10-24 的开发期，不是当前故障，但会掩盖真事件）。

## 9. 顺手修掉的一个真 bug（不是分析结论）

**现象**：审批到了 `pending_until` 仍不转 `expired`，`reminded_at` 永远为空。

**根因**：`expirePending`（`src/governance/gate.ts:1854`）的注释写着"cron 每 5 分钟"，
但全仓库搜索 `expirePending(` 只有定义处与测试调用，**装配层没有注册任何 job**。
清理/提醒逻辑都写了，没人调。

**修法**（本次提交）：在 daemon 里注册 `gov.approval-expiry`，`kind: 'light'`、
`everyMs: 5 分钟`，直接复用 `gate.ts` 的实现（别名 `govExpirePending`），
只在真的发生到期/提醒时打一行日志。水位紧张时 light job 跳轮，只推迟收敛。

**测试**：`tests/governance-approval-expiry-wiring.test.ts` 3 条静态守卫——
job 存在且调用别名函数、周期 ≤ 5 分钟、必须从 `gate.ts` 导入（防另写一套语义）。

**这条测试能证明什么、不能证明什么**：能证明"接线被删会红"；
不能证明调度器在真机上按时触发。部署后看日志里的 `[gov] 审批扫描：到期 N 条`
或 `resource_events` 即可确认。

**没做的事**：没有手动放行/暂停/重置线上任何任务与容器——那需要人工确认输入是否仍有效。

## 10. 飞书审批"批了又重置"：复现、根因、已修

### 现象与现场证据

主人 10-25 08:30 点了两次同意，卡片上的单子批完又出现一张一模一样的。库里是这条链：

| 时间 | 事件 |
|---|---|
| 08:30:06 | 任务 `tk_ev_37` 为 `shell.run` 开单 `#160`（dangerous）|
| 08:30:21 | 主人同意 `#160` |
| 08:30:22 | `claim → resolveExecution(failed)`，审计写"执行失败：no digest" |
| 08:30:50 | 模型原样重试 → 开单 `#161`（同参数）|
| 08:31:01 | 主人同意 `#161` |
| 08:31:02 | 再次 `failed`，原因同样是 `container_not_ready` |

`steps` 里两个工具步的 `result_json` 都是
`{"code":"container_not_ready","message":"容器状态 quarantined 不可派发（需 ready）","retryable":true}`。

### 三条根因

1. **容器被隔离**（`GET /api/container` → `state=quarantined`，连续 29 小时）。
   动作根本没跑起来，所以"同意"必然失败。
2. **失败原因被写错**：`resolveExecution` 把 `resultDigest`（成功时才有的摘要）
   当失败文案，于是审计里永远是"执行失败：no digest"，看不出真实原因。
3. **同参数重试会重新开单**：基础设施失败后模型重试同一命令，治理又开一张新单、
   又发一张卡 —— 主人看到的就是"批了又重置"。

### 已修（本次提交）

1. **按业务操作审批**（`src/shared/operation.ts` + 卡片重写）：
   标题用任务里的业务动作（"早间天气提醒"），正文分「业务动作 / 具体操作 /
   要做什么 / 风险 / 原始参数」；heredoc 正文只报"运行 python3 脚本（22 行）"，
   金额（分→元）、目标地址、渠道、支付/下单/TLS/删除等风险从参数里读出来。
   用线上 `#161` 的真实数据渲染结果：

   ```
   需要你决定 · 早间天气提醒（审批 #161）
   业务动作：早间天气提醒
   具体操作：运行 python3 脚本（22 行）
   档位：危险操作    工具：shell.run
   要做什么：目标地址 api.open-meteo.com/v1/forecast
   原始参数：（灰色，脱敏后原文）
   ```

2. **同参数不再重复打扰**（`gate.findReusableApproval`）：
   - 同参数还有 pending 单 → 复用同一张，不重复开票；
   - 同参数 30 分钟内批过、但执行因**基础设施**失败（`container_not_ready` /
     `container_busy` / `container_unreachable` / `transport_error`）→ 直接放行，
     审计记 `approval_reused`；
   - **spend 档不复用**、业务失败不复用、参数不同不复用、超过 30 分钟不复用。

3. **失败原因如实入库**：`resolveExecution` 新增 `errorText`，审计写成
   `执行失败：container_not_ready: 容器状态 quarantined 不可派发（需 ready）`，
   不再是 `no digest`。

测试：`tests/approval-operation.test.ts`（9 条）、
`tests/approval-card-operation.test.ts`（6 条）、
`tests/governance-approval-reuse.test.ts`（5 条，含 spend 不复用与窗口边界）。

### 仍然没有解决的（必须说清楚）

- **容器仍处于隔离状态**：不重置它，下一次审批执行还是会失败。重置会重建容器，
  属于会影响线上状态的动作，没有代主人执行。

### 11. "点外卖支付"现在是一等操作：`pay.charge`（2026-10-25 补齐）

上面那条"工具仍然只能是 shell.run"已经解决：新增 spend 档工具 `pay.charge`，
模型可以直接发起"付 35 元给美团外卖（food）"，而不是写一段 python 脚本去付款。

**形状**

- 参数：`amountCents`（正整数，**分**）、`currency`（ISO4217）、`category`、
  `payee`（必填，卡片上要写清付给谁），可选 `memo` / `orderId`。
- 执行体：`src/connectors/pay.ts`，宿主侧直连 `POST $DOTD_PAY_ENDPOINT`，
  带 `idempotency-key` 与可选 `Bearer`；2xx + `receiptId` 才算成功，
  其余一律失败且**不自动重试**（钱可能已经出去了）。
- 治理：`config/tools.yml` 里 `tier: spend` + `spendParams.required`，
  每次都必审批；审批卡正文由 `describeOperation` 翻成
  `支付 CNY 35.00 给 美团外卖`，参数行是「收款方 / 金额 / 类别 / 备注」。
- 台账：成功后写 `spend_ledger`（`kind='charge'`），当日累计也读这张表做日限额。
- 可见性：只有装配层真的注册了处理器（配了 endpoint 或 dry-run）时，
  `ExecService.visibleCaps` 才把它放进模型的工具清单 —— 没配渠道就不会
  出现一个永远失败的口子（与 `mcp.call` 同一条规则）。

**配置（都不配 = 工具不注册，行为与今天逐字一致）**

| 环境变量 | 含义 |
| --- | --- |
| `DOTD_PAY_ENDPOINT` | 渠道 HTTP 端点（必须 http/https） |
| `DOTD_PAY_TOKEN` | 可选 `Bearer` 令牌 |
| `DOTD_PAY_DRY_RUN=1` | 不真请求，返回合成回执（联调用） |
| `DOTD_PAY_MAX_CENTS` | 单笔上限，默认 100000（1000 元） |
| `DOTD_PAY_DAILY_CENTS` | 当日累计上限，默认 200000（2000 元） |
| `DOTD_PAY_TIMEOUT_MS` | 请求超时，默认 30000 |

**协议**：请求体 `{amountCents,currency,category,payee,memo,orderId}`，
成功响应至少含 `receiptId`（或 `id`）。2xx 但没有回执号 → `PAY_AMBIGUOUS`
（钱可能已扣，必须问人），5xx/429 → `PAY_REJECTED`（retryable）。

**测试**：`tests/pay-charge.test.ts`（13 条：配置解析、参数校验、单笔/日限额、
幂等复用、真本地 HTTP 服务端走完整协议、真 `config/tools.yml` 的 spend 校验、
治理端到端 → `spend_ledger` 落一条 3500 分 food）。

**仍然是"架构就位、渠道未接"**：仓库里没有任何真实支付渠道的凭证，
所以线上要真正付钱，需要主人提供一个能做支付的端点（自建网关或服务商 API）。
没有端点时模型看不到这个工具 —— 这是刻意的，不是遗漏。

## 13. 容器镜像重建：为什么"重建了却没生效"（2026-10-25 傍晚）

上一轮把归档撞名修在了 `agent-runtime/fs.ts`（`f172a3e`），但修复只在**下次构建的镜像**里，
线上容器跑的还是 10-24 的镜像。这次去重建，先发现了一个更根本的问题：

| 现象（证据） | 根因 | 修法 |
| --- | --- | --- |
| `image_builds` 里最新可用 ready 行（id=37）digest 是 `sha256:325f82…`，而 `dotd/exec:slim-0.2.1` tag 实际指向 `47db6c…`；容器跑的是 `325f82…` | `ensureImage()` 秒回**账上的 digest**，`buildSpec()` 又是 `digest ?? tag` 建容器。宿主侧 `rebuild-image.sh` 用同一个 tag 重建后，账本不更新 → 容器永远用旧镜像，而漂移检测比的正是"旧 digest vs 旧容器 ImageID"，两边一致，连漂移都不报 | `ContainerBackend.imageId(tag)`（`docker image inspect`）+ `ensureImage()` 秒回前核对实况；不一致以 docker 为准回写账本并留一条 `exec.image.build` 日志；取不到（stub/404）保持原值 |
| `rebuild-image.sh --swap` 声称"删容器让 reconcile 接手"，但 reconcile 只在 boot 跑 | 旧注释把一个只在启动时执行的动作写成了"会接手" | `--swap` 现在会优雅停 daemon（TERM，30s 宽限）再拉起，boot 里真正走 `ensureImage → reconcile` |
| `scripts/sync-to-wsl.sh` 的源目录是 `/mnt/d/toagi/dotd`（不存在） | 路径写死且早已过期，脚本每次直接 `exit 1` | 改为 `/mnt/d/dotd` |
| `wsl-deploy.sh` 的 `rsync --delete` 会删掉 `/root/dotd` 里的 `_tokens_src.env` / `_config_src.yml` | 这些是部署机本地文件、不在仓库里；删掉后下次重启带空 token 起 | 加 `--exclude '_*'` |
| `wsl-deploy.sh` 用 `daemon-launch.sh` 启动，环境变量只有 `tokens.env` 里那几个 | WSL 特有的 `DOTD_MODEL_HOST/TIER2/FLEET/NET_TOOLS/HOME/DB_PATH/CONFIG` 全丢，模型端点退回 WSL 里不通的 `127.0.0.1:3065` | 改用它本来的 `wsl-daemon.sh`；后者支持 `DOTD_REPO_DIR` |

  本来就没有 237MB 模型），但**不会再一声不响**。

### 17.10 部署时"两份都起"：watchdog 和部署脚本抢同一个进程

这轮最后一次部署，输出里出现了一条一直没解释过的行：

```text
[deploy] SIGTERM supervisor+daemon: 645338 645381
[deploy] 30s 还没退，SIGKILL: 651311 651382      ← 为什么 TERM 明明发了 30s 还没退？
[deploy] 启动 daemon（DOTD_REPO_DIR=/root/dotd）
```

第一反应是"uvicorn 关不掉"。单独验了一次 SIGTERM（临时 home、端口 7799）：
`ready: True after 7s` → `exit rc=-15 in 1.3s`。**退得很干净，不是 shutdown 挂住。**

真正的现场在两边：

- `wsl-deploy.sh` 的重启段是「TERM 旧 supervisor → 等它退干净 → 起新的」，
  中间若干秒 **7788 是故意不通的**；
- crontab 里 `*/2 * * * * /usr/local/bin/dotd-watchdog.sh`，它的 `repair_daemon()`
  只要 7788 不通就 `setsid bash scripts/dotd-daemon-start.sh`。

于是部署窗口里 watchdog 拉起**第二份 supervisor**，和部署脚本刚要起的那份抢
8000/7788。部署脚本收尾的 `pgrep` 把后来者 SIGKILL 掉，活下来的孤儿跑的是**重启前
的旧代码** —— 而日志一路绿。证据：`/tmp/dotd-wsl.log.prev` 里

```text
===== 启动 2026-10-26 01:20:01 =====     ← 同一秒两条
===== 启动 2026-10-26 01:20:01 =====
[one-system] dotd restarted（累计 2 次）
```

这不是偶发：只要部署耗时跨过某个 2 分钟边界，就会复现。

修法是三层，各自都能独立兜住：

1. **部署窗口锁**（`wsl-deploy.sh`）。重启段之前写 `~/.dotd/deploy.lock`（内容只有
   时间戳），`trap ... EXIT` 删除 —— 正常结束、`exit 4/5/6` 这类失败退出都会走；
   被 SIGKILL 时靠下面的 TTL 过期。
2. **watchdog 在锁新鲜时不自愈**（`dotd-watchdog.sh`）。`LOCK_TTL=300`，判据是
   "age < TTL"；锁文件缺失/是空/是垃圾内容一律当成**没有锁**（宁可修，也不静默躺平）。
   关键取舍：**只挡自愈，不挡检测** —— `check daemon/docker/container/relay` 仍然无条件
   执行，部署真挂了照样连续失败、照样发飞书。跳过自愈时写一行
   `自愈:部署进行中（…s 前），跳过修复`，否则下次排障又得从头猜。
3. **启动器单实例闸门**（`wsl-daemon.sh`）。`flock -n` 拿不到锁就 `exit 0`
   （"已经有一份在跑"不是错误）。用 flock 而不是 pidfile：锁跟 fd 走，进程一死内核
   自动释放，没有"残留 pidfile 导致永远起不来"这种坑；fd 会跨 `exec` 保留
   （bash → python supervisor），所以锁的生命期正好是进程的生命期。锁必须在
   `: > $LOG` **之前**拿，否则后到的那份会把正在写的日志清空。
   没有 `flock` 命令时（裁剪系统）**放行**并打一行说明：少一层保护可以，永久起不来不行。

顺手挖出两个"静默坏掉"的地方：

- `repair_container()` 的 fleet 重建分支调用 `scripts/wsl-daemon-start.sh` ——
  **该文件从来不存在**（仓库和部署副本都没有），所以这条自愈路径一直 exit 127，
  日志里却像"试过了"。改成真正的启动器 `dotd-daemon-start.sh`。
- 仓库里的 `dotd-watchdog.sh` 与 `/usr/local/bin/dotd-watchdog.sh` 是**两份文件**，
  差一行：relay 自愈的工作目录。live 那份 10-25 手工改成了 `D:\dotd`，仓库里还留着
  早已删除的 `D:\toagi\dotd` —— **照仓库重装一次 watchdog 就会把自愈改回坏的**。
  现在仓库里改对了，并且部署时用 `install -m 755` 对齐两份（`cmp` 相同则不动）。
  crontab **不自动改**（机器级状态得人拍板），仅在缺失时打一行提醒。

## 18. 收尾第四轮：体检在「看错的地方」找答案（2026-10-26 凌晨）

这一轮的起点是一句看起来最无害的话：

```text
✅ 一套系统配置 — home=/root/.dotd token=set port=7788
```

`voice-check` 绿了。但同一台机器上 `node scripts/voice-check.mjs` 的前两行是红的。
把两条输出放在一起看，才注意到**它们不是矛盾，是同一个 bug 的两面**：
检查器去错了地方找答案，然后把"我没找到"说成"你没有"。

一轮下来同一个模式抓出**七处**。判据全是同一条：
**这条红/绿，是在检查被检查对象，还是在检查检查器自己的视野？**

### 18.1 七处同型缺陷

| # | 假结论 | 它看的地方 | 真相 |
|---|---|---|---|
| 1 | `voice-check` ❌ 找不到 python | 写死 `python` | Debian/WSL 只有 `python3`；`.venv` 里的解释器根本没被考虑 |
| 2 | 连锁：❌ `--check` 失败，next 写"设置 DOTD_MASTER_TOKEN" | 解释器都没起来 | 把**工具自己的 bug** 说成用户的配置问题 |
| 3 | `/mnt/d/dotd` 下"体检通过" | 先看 `.venv/Scripts/python.exe` | DrvFs 让 Windows 解释器在 Linux 侧可见：报告 `home=C:\Users\1\.dotd`，**查的是另一台机器** |
| 4 | `onboard` ⚠️ 缺模型 key（三个） | 只读 `process.env` | 三个 key 都在 `tokens.env`，daemon source 它、模型一路正常 |
| 5 | `onboard` ✅ 主人令牌 = `config.yml` 的 `master_token` | 只判"长度 ≥16 且不含 change-me" | 那格写的是字面量 `${DOTD_MASTER_TOKEN}`，**长度 20**，是引用不是令牌 |
| 6 | 「语音设备」这一科**整行消失** | 拿上一条的假令牌请求 `/api/devices` → 401 → `catch {}` | 这一科从来没真查过；消失看起来像"没有这一项" |
| 7 | `npm run charlie:check` → `sh: 1: python: not found` | `package.json` 三条入口写死 `python` | 而 `onboard` 把 `npm run charlie:start` 当"下一步"教给用户 —— 新手第一条命令必失败 |

第 5、6 条是这一轮最贵的发现：**假绿比假红危险**。第 7 条则说明白了一个顺序问题——
体检修好了，但体检**推荐你去跑的命令**仍然是坏的，那等于没修。

### 18.2 解析顺序：写死在一处，其余全引用

新增 `scripts/lib/python.mjs`，顺序是判据：

```text
DOTD_PYTHON（显式，且只认它）→ 仓库 .venv（只认当前平台布局）→ python3 → python
```

三条约束各自都有现场：

- **显式指定就只用它**：`DOTD_PYTHON=/opt/py312/bin/python` 被后面的候选顶替，
  是"我明明指定了却跑了别的"——最难查的一类。
- **只认当前平台布局**：`.venv` 的解析**不跨平台回退**。少了匹配的平台 venv 就返回
  `null`，让调用方诚实地报"依赖没装"，而不是拿 Windows 环境冒充。
- **`python3` 在 `python` 之前**：前者是 Debian 系的唯一安装，后者常常不装或指向 py2。

`.venv` 排在 `python3` 之前，因为集成层依赖（fastapi/uvicorn/edge_tts/lark_oapi）
只装在 `.venv` 里；先找到系统 `python3` 会得出"依赖没装"，而**那种红是误导**。

`onboard` 里原来有个 `firstVersion(bin, args)`，会把 `DOTD_NODE` 也当解释器候选试
（笔误），一并删掉——那正是"复制一份解析逻辑"的代价。

### 18.3 `package.json`：npm 入口也得会挑解释器

不能简单改成 `python3`（Windows 上反过来常常只有 `python`）。新增 `scripts/py.mjs`：

```json
"charlie:start": "node scripts/py.mjs -m voice.integration.one_system"
```

- 用 `spawn` 而不是 `spawnSync`：`charlie:start` 是长驻进程，**信号必须原样转发**，
  否则 `kill <node>` 会留下一个没人管的 Python 进程占着 8000，下次启动撞端口；
- 退出码原样返回（被信号杀死时按 shell 惯例给 128+n），CI 靠它判断成败；
- 一个候选都没有时 `exit 127` 并**列出试过哪些**，而不是抛栈。

顺带修了两处"提示里的命令跑不起来"：`onboard`/`voice-check` 的 ASR 下一步原来写
`python -m voice.integration.asr_model`，现在用**已经解析出来的解释器**拼进提示里。
`setup-all` 的 `python ?? 'python'` 也去掉了——那会在没有解释器时硬跑一句
`python -m venv`，回 `python: not found`，看着像"venv 建不了"。

### 18.4 `tokens.env`：一个「有行」不等于「有值」

`onboard` 的模型 key 与令牌判定都改成 `layeredEnv`：`process.env` ∪
`<home>/tokens.env`，**进程环境优先**（显式覆盖文件，与 shell 的 source 语义一致）。
只解析 `NAME=value` 形状、**不执行**文件内容，`sources` 只记路径不记值。

要不要干脆改成"文件里有就 OK"？不行。这里必须分三档（`doctor` 用）：

| 环境里 | tokens.env 里 | 判定 | 理由 |
|---|---|---|---|
| 有 | — | ✅ ok | 现在起就能用 |
| 没有 | 有 | ⚠️ warn | `charlie:start` / `wsl-daemon.sh` 会 source 它；但裸 `npm run serve` **不** source，真会 fail-closed |
| 没有 | 没有 | ❌ fail | 怎么起都不行 |

第二档如果直接判 ok，就把一个**真实存在的启动方式**（裸 `serve`）的坑盖住了。

live 上的实际结果是诚实的：`OPENROUTER_API_KEY` / `BACKUP_API_KEY` 在
`/root/.dotd/tokens.env` 里**有行、值为空**（`len= 0`），所以只报 `HY3_API_KEY` 是
**对的**。专门加了一条测试钉住"有行 ≠ 有值"，免得以后有人把 `has()` 改成
"键名出现过"，把真缺 key 的机器报成全绿。

### 18.5 `usableToken`：`${VAR}` 是引用，不是值

第 5、6 条的根因是同一个朴素判据："长度 ≥16 且不含 change-me"。而
`init-config` 生成的 `master_token: "${DOTD_MASTER_TOKEN}"` 长度**正好 20**。

新增 `usableToken()`：太短 / 是整串 `${VAR}`（含 `${VAR:-默认}`）/ 仍是 change-me
→ `null`。`onboard` 的令牌判定与 `findToken()` 都改用它，`findToken()` 的第二来源
也从"手抄文件列表 + 手写正则"换成同一个 `layeredEnv`——**抄两份迟早会漂，而漂掉的
那份正是「语音设备」这一科的判据**。

401 不再被 `catch {}` 吞掉：现在报"令牌被拒（HTTP 401）"并指向真正的原因。
连不上与查不了也各有明确一行，不再整行消失。

### 18.6 `doctor` 的两条假红，和一条「猜测不能当结论」

`doctor` 在 live 上原来有三条假红，各自不同：

1. **`4 个严格占位符在环境里没有值`** —— 3 个在 `tokens.env` 里（见 18.4 的三档判定）。
2. **`DOTD_DB_PATH` 根本不在严格清单里。** 它曾经在，理由是 `config.yml` 写了
   `db.path: ${DOTD_DB_PATH}`。但**那一行没人读**：`loadSurfacesConfig` 只解析
   `surfaces:` 节，`db:` 节连解析入口都没有；真正的库路径由 `db/conn.ts` 的
   `resolveDbPath()` 直接读 `process.env`，缺了就回落到 `~/.dotd/dotd.db`——
   不是 fail-closed。实测（live，三个令牌齐全）：

   ```text
   env -u DOTD_DB_PATH → loaded OK port= 7788
   ```

   再说一遍那个原则：这张表是"缺了会拒启动"的唯一依据，**与实现同源**。
   凭 config.yml 里出现过就加进去，等于凭印象。

3. **`openrouter-main 连不上 127.0.0.1:3065`** —— 探的是 **models.yml 的默认值**。
   模型端点写的是 `${DOTD_MODEL_HOST:-http://127.0.0.1:3065}/v1`，而
   `wsl-daemon.sh` 给 daemon 导出的是 `http://172.17.48.1:13065`（Windows 侧 relay）。
   doctor 在裸 shell 里跑，没有那个变量，于是按默认值去探——实测：

   ```text
   127.0.0.1:3065        ECONNREFUSED
   172.17.48.1:13065     OPEN
   ```

   `expandWithDefault()` 现在返回 `usedFallback`：**用了默认值**这件事必须让调用方
   知道。默认值是"猜测"，猜出来的红只能判 warn，不能判 fail——
   否则一条猜测会把部署门禁和 CI 一起挡住。

修完 live 上的结论从「3 项会让 daemon 起不来」变成：

```text
结论：11 项检查，0 项阻止启动，4 项警告（能起，但行为可能不是你以为的那样）。
```

四条警告逐条都是真事，而且每条都说清了「我探的是哪个值、它从哪来」：
3 个严格占位符只在 tokens.env（裸 serve 会挂）、`DOTD_FLEET` 未设=stub、
tier1 用默认地址探不通、`HY3_API_KEY` 只在 tokens.env。

### 18.8 部署日志说"已写入"，grep 到的却是旧值

这一轮最后挖出来的，是上面所有体检修完之后**部署脚本自己**的一处假动作。

部署输出里一直有这么两行：

```text
[deploy] 对齐 /root/.dotd/config.yml
[align] expected_user_version 50 → 90（db.expected_user_version，第 47 行）
[align] 已写入 /root/.dotd/config.yml（备份 /root/.dotd/backups/config-….yml）
```

部署完成后我 `grep expected_user_version /root/.dotd/config.yml`，得到的是 **50**，
`telegram:` 段也还在。也就是说：日志说改了三处，磁盘上一点没变。

原因在下一步 —— `wsl-daemon.sh` §3：

```bash
cp _config_src.yml "$HOME/.dotd/config.yml"
```

**真正的 live 配置源是 `_config_src.yml`**（git 不跟踪，是部署机上的私有文件；
`rsync --exclude '_*'` 特意排除了它）。`~/.dotd/config.yml` 只是它的**产物**。
对齐脚本改的是产物，紧接着启动器把产物整个覆盖回源的内容。

三层问题叠在一起：

1. **改错了对象**：该改源，改的是产物；
2. **改了也白改**：每次启动都覆盖，所以这个"对齐"从来没有一次真正生效过；
3. **日志骗人**：`已写入 …（备份 …）` 是真话，但结论是假的 —— 它确实写了，
   只是写完立刻被抹掉。人看日志会以为配置已经对齐。

修法：

- `wsl-deploy.sh` §4.5 改成**逐个对齐两处**（源 + 产物）；
- `align-live-config.mts` 的目标版本不再写死 `90`（而 `src/daemon.ts` 里是 212、
  `db/migrations` 最大也是 212 —— 那就是"每次部署把注记从旧错改成新错"），
  改成从 `db/migrations` 推导，与 `doctor` 的 `expectedUserVersion()` 同源；
  推导不出来（读不到目录）时**不动这一行**，宁可留旧值也不编数字。

顺带把这一行的性质写清楚了：`db.expected_user_version` **从来没有被读过**
（`src/daemon.ts:823` 硬编码 `expectedVersion: 212`，`db:` 节连解析入口都没有），
它是纯注记。这次只保证它不会自己过期；要让它有约束力是另一个决定，
不在这个脚本里假装。

门禁三条（`tests/scripts-deploy-lock.test.ts` 28 → 31 条）：

| 钉住的 | 为什么 |
|---|---|
| 对齐目标里必须有 `$DST/_config_src.yml` | 只改产物 = 下次启动就丢 |
| 启动器确实会 `cp _config_src.yml` | 这条红掉才说明"只改产物"可以接受 |
| rsync 仍 `--exclude '_*'` | 否则部署会把源文件删掉 |

`align-live-config` 的测试也补了两条：从 migrations 推导（当前 212）、
推导不出来时不动。全量 **2159 条（2157 pass / 2 skip / 0 fail）**。

### 18.9 修完之后它还是不生效 —— 而且这次连日志都没有

改完 §18.8 再部署，输出是这样的：

```text
[deploy] 对齐 /root/dotd/_config_src.yml     ← 我刚加的那一行在
[deploy] 对齐 /root/.dotd/config.yml
[deploy] watchdog 已一致
```

`[align]` 一行都没有。grep 配置：**还是 50，telegram 段还在。**

这是同一句命令的第二个坑：`node --import tsx` 按 **cwd** 解析 `tsx`。部署是从
`/mnt/d/dotd` 跑的，那里的 `node_modules` 是 **Windows** 装的 —— esbuild 去加载
win32 二进制，`TransformError` 退出。而那一行后面挂着 `|| true`：

```bash

```

失败 → `|| true` 吃掉 → 部署继续 → "对齐"从 2026-10-17 起**一次都没真正跑过**。

两个教训叠在一起：

- **`|| true` 是这类 bug 的温床。** 它把"这一步没做"变成"看起来做了"。
  凡是改状态的一步，失败就该拦住后续（这里是拒绝带着配置漂移重启）。
- **跨平台副本的 cwd 会决定加载哪个二进制。** `/mnt/d` 下 `node_modules` 是 Windows
  那份，`cd "$DST"` 才用 Linux 那份。这和 §18.1 第 3 条（`.venv/Scripts` 在 WSL 可见）
  是同一个 DrvFs 现象的两个面。

修法：`(cd "$DST" && node --import tsx ./scripts/align-live-config.mts --config "$cfg")`，
去掉 `|| true`，失败打印并 `exit 7`（配置漂移不许带着重启）。

再部署一次，这次是真的：

```text
[deploy] 对齐 /root/dotd/_config_src.yml
[align] /root/dotd/_config_src.yml 已对齐（port=7788 version=212，无 telegram 段），无需修改
[deploy] 对齐 /root/.dotd/config.yml
[align] expected_user_version 50 → 212（db.expected_user_version，第 47 行）
[align] 删 surfaces.telegram 段（第 68-71 行，共 4 行）
[align] 已写入 /root/.dotd/config.yml（备份 …）
```

落盘核对（这才是判据，日志不是）：

```text
/root/.dotd/config.yml:47:  expected_user_version: 212
/root/dotd/_config_src.yml:47:  expected_user_version: 212
telegram 段: 0 处
```

注意源文件那一轮显示"无需修改" —— 因为上一步我手工跑过一次，它已经是 212 了；
真正被改的是产物，然后再启动就 `cp` 同一份 212 过去。两处同值 = 不会再被抹掉。

`tests/scripts-deploy-lock.test.ts` 再补两条（31 → 33）：对齐必须在 `$DST` 里跑、
不许 `|| true` 且失败要 `exit 7`。全量 **2161 条（2159 pass / 2 skip / 0 fail）**。

部署后 live 核对：`/api/health`(7788) / `/health`(8000) / `/console/`(8000) /
8443 全 200，`ok=true voice=ok kernel=ok asr=local`，只有一个 supervisor

### 18.10 顺着这条线又找到两处

修完 §18.9 之后继续按同一个问题扫（"这条结论是在检查对象，还是在检查检查器
自己的视野？"），又抓到两处：

**① `doctor` 检查的 MCP 配置，不是 daemon 读的那一份。**

daemon 的路径是 `process.env.DOTD_MCP_CONFIG ?? join(cfg.configDir, 'mcp-servers.yml')`，
而 `cfg.configDir` 来自 `resolveConfigDir()`：有 `DOTD_CONFIG_DIR` 用它，否则
`repoRoot/config`。托管部署（one_system）会把 `DOTD_CONFIG_DIR` 设成 `~/.dotd`
（`one_system.py:203`、`:531`），所以**真正生效的是 `~/.dotd/mcp-servers.yml`**。

doctor 原来写死 `join(repoRoot, 'config', 'mcp-servers.yml')`。后果双向：

- 用户在 `~/.dotd` 里配好了 server → doctor 说「未启用」；
- 仓库模板被改坏（比如少 `command`）→ doctor 报 fail，而那个文件没人读。

修法：`doctor` 新增 `resolveConfigDir(env, repoRoot)`，与 `src/daemon.ts` 同判据；
路径不在仓库里时，skip 的说明会补一句「仓库模板存在，但 daemon 不读它」。

**② 启动器在没装 python3 时 `exec ""`。**

```bash
PY="$PWD/.venv/bin/python"
[ -x "$PY" ] || PY="$(command -v python3)"
exec "$PY" -m voice.integration.one_system --port 8000
```

`command -v python3` 也失败时 `PY` 是空串，第三行变成 `exec "" …`，终端只会看到
`: not found` —— 读起来像脚本语法坏了。真相是"这台机器没有 Python"。

这类"空变量传下去"和 §18.1 第 2 条（工具 bug 说成用户配置问题）是同一个形状：
**错误的措辞把责任指错了对象**。现在显式判空 + 判可执行，给安装命令，`exit 1`。

门禁：doctor 26 → 28（默认路径跟随 `DOTD_CONFIG_DIR`、运行时那份缺失时点明模板不生效）；
deploy-lock 33 → 35（闸门必须在 `exec` 之前；把闸门那段**原样切出来**在临时目录里真跑，
PATH 里没有 python3 → 必须 `exit 1` + `找不到 Python`）。全量 **2165 条
（2163 pass / 2 skip / 0 fail）**，`tsc --noEmit` 干净。

到这里这条线已经收敛：剩下的 `|| true` / `catch {}` 逐个看过了，都是"轮询等启动"
「非 JSON 响应」这类**有意**吞掉的；`verify-cas-direct.sh` 里的 `python` 只出现在一句
echo 里，不是命令位置。

### 18.11 同一条线再深一层：配置目录、引号、假链接

§18.10 之后继续用同一个问题扫（"这条结论在检查对象，还是在检查检查器自己的视野？"），
又抓到四类，全部是**同一个判据被抄了三份**的后果。

**① 配置目录判据被抄了三份，三处看的都不是 daemon 读的那份。**

daemon 的路径是 `cfg.configDir` = `resolveConfigDir()` = `DOTD_CONFIG_DIR ?? repo/config`。
`models.yml` 从 2026-10-25 起还是**热加载**的 —— 托管部署里主人改的是
`~/.dotd/models.yml`，改完不用重启就生效。而三个审计脚本各自写死仓库模板：

| 脚本 | 原来读的 | 后果 |
| --- | --- | --- |
| `doctor.mjs`（tier1） | `repoRoot/config/models.yml` | 运行时端点被关掉，daemon 已经在挂起，doctor 还报 ok |
| `onboard.mjs`（模型 key） | `repoRoot/config/models.yml` | 按模板里的 `api_key_env` 数 key，与真正生效的配置无关 |
| `probe-live-model.mjs` | `repoRoot/config/models.yml` | 「上线前体检」验的是另一份端点 |

修法：判据收进 `scripts/lib/env.mjs` 的 `resolveConfigDir({env, repoRoot, home})`，
doctor / onboard / probe 全部引用它；`doctor` 保留同名导出，老调用方与测试不用改。
`probe-live-model` 读不到时还会补一句「仓库模板存在，但 daemon 不读它」。

**② `parseTier1Endpoint` 不去引号，`enabled: false` 还被当成"能用的端点"探活。**

两个都是"体检与真正的解析器不一致"：

- `src/router/config.ts` 的 `scalar()` 会剥掉标量两端引号；doctor 的正则直接把
  `base_url: "http://…/v1"` 的引号当值的一部分，于是判「不是合法 URL」——
  配置完全合法，红的是体检。现在加了 `unquote()`，与 router 同口径。
- `endpoints.find(enabled) ?? endpoints[0]`：tier1 **全被 `enabled: false`** 时，
  路由器的 `pickCandidates` 过滤后一个候选都没有（primary 轨真的无处可去），
  而 doctor 兜底到那个被禁用的端点去探 TCP —— 探通了就报 ok。
  「唯一的主端点被关了」这件最该拦住的事，被"反正有个地址能连"盖住了。
  现在单独判 FAIL 并直说「全部 enabled: false」，给「改成 true」的下一步。

**③ 提示里的命令不存在。**

`dotd task <不存在的 id>` 的 404 提示写的是「可用 `dotd queue` 看待办」。
`dotd queue` 从来没注册过（`buildCli()` 里没有），敲下去得到
「未知命令：queue」+ exit 2 —— **下一步提示把人指到了另一堵墙上**。
改成 `dotd status`（队列 + 熔断 + 待批审批）。

同一类还有一处：`src/daemon.ts` 保险库解密失败的提示写 `dotd vault put`，
而 CLI 只有 `vault add|list|rm`。改成 `dotd vault add`。

防回归：`tests/surfaces-cli.test.ts` 加了一条**扫描式**断言 —— 把 `cli.ts` 里
所有非注释行的 `dotd <命令>` 抽出来，逐个核对 `buildCli().commands`。
它还带一个"至少扫到 5 处"的下界，否则正则一失效这条测试就变成永远绿
（那正是本仓库反复踩的"检查器看不见自己"）。

**④ 连接总览说的不是它知道的事。**

`mcpRows()` 的 `detail` 原来是 `${toolCount} 个工具`，注释写着"能列出来就说明
已经握手成功过（toolCount 是握手拿到的事实）"——**这句是假的**：
`loadMcpServers()` 只解析 YAML，`McpClient.listTools()` 要等真正调用时才跑，
`toolCount` 是配置里 `allow_tools` 白名单的条数。command 写错、机器上没有那个
可执行文件，这里照样显示 connected + "N 个工具"。

改法：detail 变成「已声明（白名单 N 个工具）」/「已声明（未限制工具白名单）」，
并把注释改成事实。`status: 'connected'` 保留（控制台/脚本在读它，改语义要单独决定）——
先把话说准，不让人以为这里探过活。

同一处 hint 也修了：`config/mcp-servers.yml` / `config/models.yml` 都是仓库模板，
daemon 读的是 `<configDir>/`（通常 `~/.dotd/`）。写成"在 config/… 里加"会让人去改
一份没人读的文件。

门禁：doctor 28 → 30（运行时 `models.yml` 的 tier1 全禁用 → FAIL，且指出看的是哪个文件；带引号的 base_url 要按 router 的口径去引号）；
env-layered 18 → 22（`resolveConfigDir` 的四种输入：未设/设了/`~`/相对路径）；
cli 28 → 29（提示里的命令必须真存在）。全量 **2172 条（2170 pass / 2 skip / 0 fail）**，
`voice:test` 22 条全绿，`tsc --noEmit` 干净。

### 18.12 一份"官方示例 + 官方命令"能把系统弄挂

§18.11 扫的是"检查器看错地方"。这一轮从另一个角度问同一个问题：
**文档里教的启用命令，照着敲一遍，系统会不会挂？**

答案是会。`docs/voice-merge.md:173` 写着

```bash
cp config/mcp-servers.voice.yml config/mcp-servers.yml
```

而那份示例里有两处**必然失败**的东西，`npm run voice:check` 当时只判
`existsSync(示例)`，所以一路 ✅。

**① `allow_tools` 写成块列表，解析器读成"新 server"。**

示例的形状是

```yaml
    allow_tools:
      - goodnight
      - execute_scene
```

`parseMcpServersYaml` 只认行内 `[a, b]`。它把 `- goodnight` 当成下一条 server
的起始行 → `name` 为空 → 抛「某个 server 缺 name」。`loadMcpServers()` 的注释写着
"解析失败一律抛错**拒启动**" —— 所以 `cp` 完重启，daemon 根本起不来。
一份示例 + 一条官方命令 = 生产不可用，这是最坏的一类缺陷。

修法：`applyKeyValue` 的返回值从 `boolean` 改成
`'env' | 'allow_tools' | 'args' | null`，空值的 `allow_tools:` / `args:` 开启块列表；
循环里记录 `listKey` / `listIndent`，**在"新 server"判断之前**吃掉更深缩进的
`- item`。顺带修了 `args:` 的同类写法（文档里没人写过，但形状是对称的）。

**② `command: python` 在这台机器上不存在。**

live 实测：

```
$ command -v python    → 没有
$ command -v python3   → /usr/bin/python3
$ python3 -c 'import mcp' → ModuleNotFoundError: No module named 'mcp'
$ /root/dotd/.venv/bin/python -c 'import mcp' → ok
```

Debian/Ubuntu/WSL 默认只装 `python3`；而依赖装在仓库 `.venv` 里。所以示例的
`command: python` 有两重错：命令不存在，就算改成 `python3` 也缺 `mcp`。
这正是 §18.1 那批"写死 `python`"的同一件事，只是这次藏在**配置文件**里，
所有 Node 侧的门禁都看不见。

修法：示例改成 `command: node` + `args: ["scripts/py.mjs", "voice/charlie/magic-scenes.py"]`。
`scripts/py.mjs` 就是仓库里所有 Python 入口用的解析器（显式 `DOTD_PYTHON` →
当前平台 `.venv` → `python3` → `python`），它把 stdio 原样透传，JSON-RPC 帧不受影响；
且它自己 `cwd=仓库根`，所以后面那个 `.py` 的相对路径与 daemon 从哪儿启动无关。
实测两个 server 都能起来：

```
scenes:    goodnight,good_morning,movie_time,leaving_home,learn_protocol,list_protocols,execute_scene
reminders: add_reminder,list_reminders,delete_reminder,set_timer,get_calendar_today,schedule_task,list_alarms
call: true "[内置] 晚安: 触发词「晚安、睡觉、好梦、睡了、我累了、goodnight」, 4步…"
```

**③ 同一条判据又被抄了一份。**

上面两个问题都要求"把示例当成真配置核一遍"。`doctor` 里已经有 `parseMcpServers`
（裸 node、不依赖 tsx）和 `resolveCommand`，但 `voice-check` 一行都没用。
第一版让 `mcp-example.mjs` 去 import `doctor.mjs`，而 `doctor.mjs` 又要 import
`mcp-example.mjs` 的 `looksLikePath` —— 两个模块互相 import，靠 ESM 提升侥幸能跑。
最后拆成两层：`scripts/lib/command.mjs`（command 存不存在，纯路径判断）、
`scripts/lib/mcp-example.mjs`（拿解析结果逐条核对）。`doctor.resolveCommand`
只剩转手，实现只在一处。

**④ 重启会把主人配好的 MCP 声明静默改回空表。**

顺着 `cp` 这条线查重启路径时发现的：`scripts/wsl-daemon.sh` §3.5 每次启动都

```bash
for f in config/*.yml; do cp -f "$f" "$HOME/.dotd/$(basename "$f")"; done
```

注释理由是"这些文件本就是 `${ENV}` 占位驱动，不含环境事实"。对 `models.yml` 成立，
对 `mcp-servers.yml` **不成立** —— 它写的是主人决定接哪些外部程序。
而文档教人的启用方式正是"把示例放到 `~/.dotd/mcp-servers.yml`"：
下一次重启就 `cp -f` 回去，MCP 又没了，日志里一个字都没有。

门禁：

### 18.13 「体检看模板、daemon 跑运行期」的最后一处：`DOTD_CONFIG_DIR` 只注入了子进程

§18.11–18.12 修的都是"某处写死了仓库 `config/`"。修完 deploy 之后，live 上
`node scripts/doctor.mjs` 仍然打出：

```
⏭️  未启用 — /root/dotd/config/mcp-servers.yml 里没有声明任何 server（servers: []）
```

而运行期那份是 `/root/.dotd/mcp-servers.yml`（两份此刻内容相同，所以行为没差，
但**审计对象是错的**：主人以后在 `~/.dotd/mcp-servers.yml` 里配好 server，
doctor 依然报"未启用"，因为它在看仓库模板）。

**根因不在 doctor。** `/proc/<dotd-pid>/environ` 里有
`DOTD_CONFIG_DIR=/root/.dotd` —— 但那是 `one_system._spawn()` 注入给 **dotd 子进程**的：

```python
env["DOTD_CONFIG_DIR"] = str(self.paths.config_dir)   # one_system.py:531
```

`scripts/wsl-daemon.sh` 导出了 `DOTD_HOME` / `DOTD_DB_PATH` / `DOTD_CONFIG`，
**唯独没有 `DOTD_CONFIG_DIR`**。于是人手动跑任何审计脚本（doctor / onboard /
probe-live-model / voice-check）时，那个 shell 里没有该变量，
`resolveConfigDir()` 回落到仓库 `config/` —— 检查器看的是模板。

两处修法，一层是配置、一层是推断：

1. **启动器导出它**（`scripts/wsl-daemon.sh`）：`export DOTD_CONFIG_DIR="$HOME/.dotd"`，
   与 `DOTD_HOME` 同一个目录。正常部署下"daemon 读的"与"审计看的"从此由同一个
   变量决定，不需要猜。
2. **判据本身补齐两条**（`src/daemon.ts` 与 `scripts/lib/env.mjs` 同步）：
   - `DOTD_CONFIG_DIR` → `DOTD_CONFIG` 所在目录 → `<home>/.dotd/models.yml` 存在时的
     `<home>/.dotd`（**托管布局的记号**）→ 仓库 `config/`；
   - 这样即便有人绕过启动器（`npm run serve` 直接起在托管机上），daemon 也不会去读
     仓库模板，而读与体检相同的那一份。
   - `configDirIsHostedGuess()` 专门回答"这条路径是推断出来的吗"，doctor 的明细里会
     写明「DOTD_CONFIG_DIR 未设，按 …/models.yml 存在推断为托管布局」——推断必须说出来，
     否则下一个人还是会以为那是显式配置。

同步钉住的还有两条判据一致性：

- `src/daemon.ts::resolveConfigDir()` 与 `scripts/lib/env.mjs::resolveConfigDir()`
  现在**必须逐项同结果**（`daemon-assembly` 新增一条：6 组 env × 2 种布局对照跑，
  任何一侧改动都会红）。写这条时才发现一个更隐蔽的漂移：TS 侧展开 `~` 用的是全局
  `homedir()`，而脚本侧用注入的 `home` —— 测试注入时两边算出的路径不同，那条
  "同判据"的断言自己假绿。现在两边都按同一个 `home` 展开。
- `DOTD_HOME` 参与托管布局判断（`CHARLIE_HOME=/data` 这类部署里配置目录不在
  `~/.dotd`）。只认 `~/.dotd` 会把 Docker 布局判错。

**`config.yml` 是另一套根，刻意不改。** `models.yml` / `mcp-servers.yml` /
`tools.yml` / `rules.yml` 走 `<configDir>`，而 surfaces 配置走
`DOTD_CONFIG ?? ~/.dotd/config.yml`（`src/surfaces/config.ts:486`）。这是有意的：
两份文件的"身份"不同 —— 前者是运行期配置目录，后者是**指向它旁边那个文件的路径**。
部署里两者同处（`~/.dotd/config.yml` + `DOTD_CONFIG_DIR=~/.dotd`），Docker 里也同处
（`/data/config.yml` + `CHARLIE_HOME=/data`）。把它也并进 configDir 会让"我只想换个
config.yml"变成"顺便换了整棵配置目录"，所以这里只把差异写进注释，不动行为。

门禁：
- `daemon-assembly` 7 → 8（daemon 与审计脚本判据必须逐项一致 + 托管布局真被认出）；
- `scripts-env-layered` 22 → 27（`DOTD_CONFIG` 分支、优先级、托管记号、开发机不误判、
  显式配置时不做推断）；
- `scripts-doctor` 31 → 34（托管布局下读 `~/.dotd` 那份；推断要写进明细；显式配置不说成推断）；
- `scripts-deploy-lock` 38 → 41（④e：启动器必须导出 `DOTD_CONFIG_DIR`、必须与
  `DOTD_HOME` 同值、真跑一遍让 `resolveConfigDir` 落在 `$HOME/.dotd`）。

全量 **2202 条（2200 pass / 2 skip / 0 fail）**，`voice:test` 22 条全绿，`tsc --noEmit` 干净。

## 18.14 「实际生效值」的第五例：体检/probe 都在看人类那个 shell

§18.13 修完 configDir 之后，同一台 live 机器上还剩两处同类缺陷。它们不是配置写错，
而是**检查器用自己 shell 的视野下结论**：

```
$ npm run doctor
⚠️  DOTD_FLEET 实际生效值让人意外
    DOTD_FLEET 未设置 → 实际生效 stub（不起容器）
⚠️  openrouter-main 的默认地址 127.0.0.1:3065 连不上

$ tr '\0' '\n' < /proc/<dotd-pid>/environ | grep -E 'FLEET|MODEL_'
DOTD_FLEET=docker
DOTD_MODEL_TRANSPORT=real-http
DOTD_MODEL_HOST=http://172.17.48.1:13065
```

容器在跑、模型在出字、网关在 13065；而体检报"stub / 3065 连不上"。这和
§18.11–18.13 是同一个病：**`DOTD_FLEET` / `DOTD_MODEL_HOST` 由启动器导出给 daemon
子进程**，人手动跑 `npm run doctor` 的交互式 shell 里没有，于是 doctor 把自己那份
"缺席"写成了机器结论，还用了「实际生效」四个字。

### 修法：两栏，而不是一栏

新 `scripts/lib/live-daemon.mjs` 从 `/proc` 读**在跑的那个 daemon**：

| 能力 | 说明 |
| --- | --- |
| `scanDaemons()` | `/proc/<pid>/cmdline` 匹配 `src/daemon.ts`，排除自身 pid；非 Linux（无 `/proc`）返回 `[]` |
| `parseProcEnv()` | `/proc/<pid>/environ` 是 NUL 分隔，不是换行 |
| `overlayRuntimeEnv()` | 只覆盖 `RUNTIME_KNOBS` 白名单；**空串不覆盖**（daemon 里空值等于没设，不该把 shell 的值抹掉） |
| `liveDaemon()` | 0 个 → `null`；1 个 → `{pid, env, overlaid}`；多个 → `{ambiguous}`，不挑一个当代言人 |

doctor 因此分成两栏，判据是"这个值决定的是**行为**还是**这个 shell 的身份**"：

- `runtimeEnv`（运行期）：fleet、model-transport、端点地址展开、configDir、db 路径、
  MCP 文件路径 —— 这些问的是"机器上现在是什么样"，必须看 daemon。
- `shellEnv`（当前 shell）：`STRICT_ENV_KEYS` 的占位符检查 —— 问的是"**从这个 shell
  启动**能不能展开"，交互式 shell 不 source tokens.env 是事实，与 daemon 有没有 key
  无关。这一栏若也改成运行期取值，就会把"裸 shell 起不来"这个真问题掩盖掉。

`RUNTIME_KNOBS` **故意不含任何 key/token**：白名单越宽，越可能把凭据经日志带出去；
而且身份类变量（`DOTD_MASTER_TOKEN`）本来就该由调用方显式给。

`/console/` 不经过这里：`src/surfaces/http.ts` 没暴露 fleet/transport，走 HTTP 取不到
（考虑过加路由，为了一个体检值在对外接口上开洞不划算）。

### 18.14.5 第十一例：所有实验脚本的「重启」都是空操作

上一节修的是"改错地方"。这一节是同一条线上更贵的一处：**动作错地方**。

2026-10-25 起 dotd 由 `voice/integration/one_system.py` 托管，启动链变成：

```
人的 shell → bash scripts/wsl-daemon.sh → python -m voice.integration.one_system
                                          └→ node src/daemon.ts（子进程，崩溃自动重启）
```

而仓库里十四个实验 / 运维脚本还停在"单进程"时代，全都写着同一段：

```bash
pkill -9 -f 'src/daemon.ts'
sleep 3
DOTD_MAX_RUNNING=2 nohup setsid bash scripts/wsl-daemon.sh >/dev/null 2>&1 < /dev/null &
```

三个后果，一个比一个隐蔽：

1. **杀的是子进程。** supervisor 两秒后按退避把它重启 —— 新子进程继承的是
   **supervisor 的环境**，不是这行 `DOTD_MAX_RUNNING=2`。所以「以并发 2 重启」
   是假的：真额度仍是启动 supervisor 时的 3。脚本接下来照跑、照打印
   「观察到最大并发 running = N」，只是 N 和 2 无关 —— 而且**没有断言**。
2. **第三行一次都没启动过任何东西。** `wsl-daemon.sh` 的单实例闸门看到锁还被
   supervisor 持着，直接 `已有实例持锁 → exit 0`。实测：

   ```
   $ DOTD_MAX_RUNNING=2 bash scripts/wsl-daemon.sh
   [wsl-daemon] 已有实例持锁（/tmp/dotd-one-system.lock），本次不启动
   $ echo $?
   0
   ```

   `fuser -v /tmp/dotd-one-system.lock` → `root 720591 F.... python`（就是 supervisor）。
   而它是以 `&` 起的、输出进 `/dev/null` —— **失败完全不可见**。
3. `pkill -f 'src/daemon.ts'` 会匹配到**执行脚本的 shell 自己**（命令行里带这串字）。
   本项目已经因此杀掉过一次工具 shell。

修法：新增 `scripts/lib/daemon-restart.sh`，与 `model-switch.sh` 同构 ——
**把判据收成一处，并且读回验证**：

| 步骤 | 作用 |
| --- | --- |
| `daemon_pids` / `daemon_supervisor_pids` | 按 argv 精确识别（`src/daemon.ts` 或 `dist/daemon.js` / `voice.integration.one_system`），绝不用 `pkill -f` |
| 停 | 有 supervisor 就停 supervisor（它退出时带走子进程），**不**单独杀子进程 |
| 等锁 | `_dr_wait_lock_free`：锁 30s 不释放就**拒绝启动**，而不是静默 exit 0 |
| 起 | `env KEY=VAL sh -c "$DAEMON_RESTART_START"` —— 环境交给**新 supervisor** |
| 验 | 回头读 `/proc/<新 pid>/environ`，读不到就 `[restart] ✗ KEY 没生效：运行期=X（期望 Y）` 并非零退出 |

启动命令与就绪探针都做成可注入（`DAEMON_RESTART_START` / `DAEMON_RESTART_PROBE_CMD`），
既让 Git Bash（没有 `setsid`/`flock`）能跑，也让测试不必真起一个 daemon。

顺手修掉三处"找不存在的东西"：

- **`run-diag.sh`**：`export DOTD_DIAG_INV=1` 重启后 `grep 'DIAG-INV'`。实测
  `DOTD_DIAG_INV` **没有任何代码读它**，`DIAG-INV` 标记从来没被打印过。找不到时它打印
  「(无输出 —— buildMessages 没走到诊断点)」—— 把"我在找不存在的东西"说成了
  "被测代码有问题"。改为 grep 真实存在的两行（`runner: tool.list 原始返回 <task>`、
  `runner: 工具清单 <task>：发现 N 个自造工具`），并把 `tool.list` 失败与"注入失败"
  分开报。
- **`verify-summary.sh`**：`grep 'DIAG-SUM'`，而 `DIAG-SUM` 在 `src/daemon.ts:756`
  只是**注释里的举例**，没有发射点。改为三段真判据：装配层是否转发
  `refreshContextSummary`（2026-10-19 那次 422 线程全 null 的根因）、
  `runner: 已更新会话摘要 <task>/<thread>`、`mem_threads.context_summary` 长度。
- **`ab-models.sh:90` / `selftest-model-down.sh:92`**：`cp /tmp/models*.bak config/models.yml`
  恢复一份**早已没人创建**的备份（创建行在 `6c55675` 被删）。文件不存在 → 这条 `cp`
  成了脚本的**退出码**：断言全过也可能 exit 1。删掉，恢复交给 `model-switch.sh` 的 trap。

还有两处"判据有两份，靠人工保持一致"：

- **`verify-goal.sh`** 数 `config/tools.yml` 的白名单条数，daemon 读
  `<configDir>/tools.yml`。live 上两份此刻**内容相同**（实测 models / tools / rules /
  mcp-servers / free-models / event-rules 全部 SAME）—— 正因为没差才危险。抽出
  `scripts/lib/config-dir.sh`（与 `scripts/lib/env.mjs::resolveConfigDir` 逐条对齐），
  `model-switch.sh` 与 `verify-goal.sh` 都改用；读不到文件时**不再当"白名单 0 个"**。
- **`live-daemon.mjs` / `daemon-restart.sh`** 只认 `src/daemon.ts`。而
  `one_system.dotd_command()` 有 `dist/daemon.js` 时**优先用它** —— 一旦有人跑过构建，
  体检就会报「看不见运行中的 daemon」，再拿自己 shell 的环境当"实际生效值"。
  两处都补上 `dist/daemon.js`。

`selftest-true-concurrency.sh` 另补上它一直缺的**断言**：并发度超过额度 = 额度没生效，
不到额度 = 根本没并发起来，两种情况都不许当成"通过"。

`rebuild-image.sh --swap` 的停/起也改走库（原来自己 `pgrep -f` 停、`setsid … > /tmp/dotd-wsl.log`
起 —— 那句重定向会把 daemon 正在写的活日志清零）。

**同一台机器上紧跟着发现的第十二例：实验改过的旋钮没人还原。**
上面那些脚本都以 `daemon_restart DOTD_MAX_RUNNING=1` 的方式改**运行期**旋钮，
跑完谁都不改回来。实测 live 上本来是 3，跑一次 `verify-vision-final.sh` 之后
它永久变成 1（串行），而脚本最后一行是「✅ 全部通过」—— 主人只看到"验证通过了"，
看不到"你的系统从此一次只跑一个任务"。

修法与 `model-switch.sh` 的 EXIT trap 同一条判据：**实验改动必须自己收尾**。
`daemon_restart` 在改旋钮前记下**旧进程里的原值**，并注册一个退出钩子，
退出时用原值再重启一次并**读回验证**；还原失败要大声说（不许静默留在实验值）。

这里踩到一个 bash 事实：**EXIT trap 只能有一个**。`model-switch.sh` 原本
`trap models_restore EXIT INT TERM`，`daemon-restart.sh` 再 `trap … EXIT` 会
**静默顶掉**它 —— 于是模型配置留在被改状态，或者额度留在 1，脚本照常退出、什么都不说。
所以新增 `scripts/lib/exit-hooks.sh`：一张钩子表，谁注册谁跑，互不覆盖
（顺带修掉"`trap … INT TERM` 在信号里继续跑而不是退出"的隐患）。

`selftest-crash.sh` 是反过来的情形：它**故意**只 `kill -9` 子进程（要验的就是崩溃自动
恢复），但恢复后又自己 `nohup setsid bash scripts/wsl-daemon.sh &` —— 在托管模式下
那句同样是空操作，而它的等待条件是"端口通"，旧 daemon 刚被杀、端口本来就断着，
所以"等到了"这件事本身没毛病。改法：等**新 pid**（而不是等端口），并且只在
"没有 supervisor"时才自己拉起 —— 有 supervisor 就该由它拉，那正是这个脚本要测的东西。

另有一处 stderr 噪音值得记：`tr '\0' '\n' < /proc/<pid>/cmdline 2>/dev/null` 里
重定向是**从左到右**生效的，`<` 先执行、`2>` 还没生效，进程扫描途中退出的那些 pid
会刷一屏 `No such file or directory`。写成 `2>/dev/null < …` 才安静 —— 而"刷屏"
的后果是人会把噪音当故障，又是一次"检查器把自己的盲点说成别人的问题"。

测试：

- `tests/scripts-daemon-restart.test.ts`（28 条）：假 `/proc` 驱动分类/停机/等锁/读回，
  外加**真起一个子进程**证明 `/proc/<pid>/environ` 这条路在真机上成立
  （关键细节：子进程必须在 bash 里起 —— Node 的 `spawn` 给的是 Windows pid，
  Git Bash 的 `/proc` 认的是 MSYS pid，实测 32708 vs 63723，完全对不上）；
  以及"十四个调用方都必须 source 库、不许再有 `pkill` + `wsl-daemon.sh`"。
- `tests/scripts-log-markers.test.ts`：脚本 grep 的每个日志标记，必须在 `src/` 或
  `voice/` 的**非注释行**里真出现过；另加一条"脚本里设的 `DOTD_*DIAG*` 开关必须有代码读"。
- `tests/scripts-config-dir.test.ts`：bash 侧与 Node 侧对同一组环境（6 种组合 + `~` 展开）
  必须给出同一个答案 —— 这是"判据只有一份"的证明。

变异验证：把 `daemon_restart` 的停机步骤改回"只杀 `daemon_pids`"→ ② 立刻红；
把读回验证删掉 → ④ 立刻红；把锁等待去掉 → ③ 立刻红；

把 `DAEMON_RESTART_RESTORE` 的默认值改成 0 → ④b 的三条立刻红；
拿掉 `_dr_remember_original` 里的 `RESTORE` 闸门 → "RESTORE=0 的那一次不记账"立刻红；
还原成功后不清账 → "还原是幂等的"立刻红。

还有一条**没能**用变异证明的：把"还原那次重启"的 `DAEMON_RESTART_RESTORE=0`
前缀改写成显式存/设/还，28 条全绿 —— 说明两种写法在这个调用深度上等价
（bash 的前缀赋值在整个动态作用域内生效，实测 `f(){ h; }; V=0 f` 里 `h` 读到 0）。
所以代码里留的是短写法，并在注释里写明"实测等价"，不再声称它会二次还原。

### 18.14.6 第十三例：看门狗"修好了"附带把系统降成串行

**现场（代码里，不是推断）**：

```bash
repair_daemon() {
  DOTD_MAX_RUNNING=1 setsid bash scripts/dotd-daemon-start.sh …   # ← 写死 1
}
```

而启动器里是：

```bash
# scripts/wsl-daemon.sh:145
export DOTD_MAX_RUNNING="${DOTD_MAX_RUNNING:-3}"
```

`:-` 的语义是"没传才用 3" —— **传了 1 就保住 1**。实测：

```
$ DOTD_MAX_RUNNING=1 bash -c '…export DOTD_MAX_RUNNING="${DOTD_MAX_RUNNING:-3}"…'
launcher_effective=1
$ bash -c '…同上…'                       # 不传
launcher_effective=3
```

于是这条链路成立：daemon 挂了（凌晨、无人值守）→ cron 每 2 分钟的看门狗自愈 →
**系统从 3 并发变成永久串行**，而日志只有一行「自愈:daemon 已恢复(6s)」。
主人看到的是"修好了"，看不到"修好之后一次只跑一个任务"；cron 会一直这么修，
没人会去复核。这和第十二例是同一个形状：**一个动作改了运行期参数，却只报告它想报告的那部分**。

`repair_container()` 的第二条路径（fleet 重建）同样带着 `DOTD_MAX_RUNNING=1`，
同一个病。

**为什么当初会写 1**：那段是 2026-10-19 加自愈时一起写的（`a9e3f13`），
当时的语境是"故障恢复时保守一点，别一上来就三并发"。保守本身没错，
错在**保守值被永久继承**，且日志不说。

**修法**（两件事，缺一不可）：

1. 启动行去掉 `DOTD_MAX_RUNNING`（两处）。自愈只该恢复**可用性**，
   不该顺带调参；要调额度就由人显式传。
2. 「已恢复」那行带上**运行期实际值**：`live_max_running()` 读
   `/proc/<pid>/environ`（与 `scripts/lib/live-daemon.mjs` 的识别规则一致，
   同时认 `src/daemon.ts` 与 `dist/daemon.js`），日志变成
   `自愈:daemon 已恢复(6s)（DOTD_MAX_RUNNING=3）`。
   端口通 ≠ 参数对；以后谁再顺手改，日志里能对上，不用等人发现"怎么突然变慢了"。

**测试**（`tests/scripts-deploy-lock.test.ts` 新增 ⑤ 组，5 条 + 该文件原有 43 条）：
`launcherLine()` 只取"启动 daemon 的那一行"来判有没有前缀赋值 —— 第一版守卫扫
整段函数体，把新加的**读出来写日志**那行 `DOTD_MAX_RUNNING=$eff` 判成"写死额度"，
是"判据比事实宽"的又一次。另外三条钉住日志必须带实际值、读的是 `environ`
而不是配置文件、以及假 `/proc` 里 supervisor 也带同名变量时**必须取 daemon 那个**
（取错就会把 supervisor 的 9 当成额度）。

**变异验证**：把 `DOTD_MAX_RUNNING=1` 加回启动行 → 立刻红；日志去掉额度 → 立刻红；
`live_max_running` 改成认 `voice.integration.one_system` → 两条红。

**这条修正不能证明什么**：不能证明 live 上已经被降过档。`/tmp/dotd-wsl.log`
与 `.prev` 里都只有 `Runner 消费者已启动 3 个（DOTD_MAX_RUNNING=3）`，
当前 supervisor 的 environ 也是 3 —— 也就是说**这次没被抓到现行**，
但机制是通的（上面那条 `launcher_effective=1` 就是证据），
且 2026-10-26 01:20 确实发生过一次自愈成功。
