## S6 探针不检查容器在线（2026-10-19 第 20 轮发现，判据外，未修）

`soak.sh probe` 只验三件事：答案对、飞书出站成功、飞书入站长连接在。
**不验容器是否在线**。所以容器挂掉的 6 小时里，探针照样报"成功率 100%"。

当前的兜底是 `container_up` 采样点（第 20 轮已补末尾在线率 + 连续离线上限），
但那只是"容器进程在不在"，不是"任务能不能真的跑"。
真要严格，探针应该真跑一次需要容器的任务（比如读 `/dot/home/q3-sales.txt`），
容器挂了就该失败。

不在 S6 判据文字内（判据只说"成功率不掉/无人工干预/内存/句柄"），
且加进去会让探针变慢、成本变高，所以先记着不动。

## daemon RSS 呈阶梯式爬升 —— **已定位：是 V8 分配器扩容，不是泄漏**（2026-10-20）

> 本文档先后写过两个错结论，都记在这里，因为错在哪里比结论更有用。
>
> **第一次错（10-19 夜）**：写"稳定爬升 ~10MB/h、7 天外推 1.5GB、超判据 30 倍"。
> 错因：用 3~5 分钟窗口的单调上升外推长期趋势。
> **第二次错（10-20 01:2x）**：写"是阶梯式爬升，可能漏，继续观测"。
> 错因：只描述了形状，没做定性的实验。
>
> **现在有实验证据了。**

### 实验：一秒一次的 `db.prepare()`，跑 280 秒

| 时间 | RSS |
|---|---|
| t+20s | 45.5MB |
| t+40s | 46.1MB |
| t+120s | 46.1MB ← **80 秒完全持平** |
| t+140s | 47.2MB |
| t+240s | 47.2MB ← **100 秒完全持平** |
| t+280s | 47.7MB |

**阶梯形状与真实 daemon 完全一致**：涨一级 → 长时间持平 → 再涨一级。
280 秒总共只涨 2.2MB，且每一级之后都稳定下来 —— 这是 V8 堆/分配器扩容的特征，
**不是泄漏**。真泄漏不会持平。

补充证据：
- `heapUsed` 全程几乎不动（4.5 → 4.7MB）→ 没有 JS 对象累积。
- 显式 `global.gc()` 对 RSS 无效 → RSS 里是已提交但未使用的页，不是可达对象。
- 对比实验：同样负载下 `prepare()` **不缓存** 4 分钟涨 4.3MB，
  **缓存** 只涨 1.7MB —— 不缓存确实更费，但两者都趋于平台，不是无界。

### 仍然值得做（但不阻塞 S6）

`src/control-plane/scheduler.ts` 的热路径（`scanCrontabs` 每秒 1 次等）每次
`db.prepare()` 都新建语句对象，`db/conn.ts` 没有任何 prepared statement 缓存。
这不造成泄漏，但会造成**阶梯更频繁、上限更高**。合理的改法是加一层
以 SQL 文本为 key 的语句缓存（或改用 `db.prepare` 一次、闭包持有）。
**等 S6 判据真的因 RSS 失败再动**——现在动等于在 7 天窗口中间改代码。

### 对 S6 的意义

判据 `RSS 增幅 < 50MB` 本身没问题（它如实反映了 36MB 的净增）。
但**"每段都在爬 ≥2MB/h"这条子判据对阶梯式增长会误报**：
一段 1.1 小时的窗口恰好覆盖"涨一级"，斜率就是正的且很大。
真正的泄漏特征是**永不持平**，而阶梯式**会持平**。
若要修，正确方向是看"段内是否出现过持平区间"而不是纯斜率——
但这属于判据调优，需要先有足够长的真实数据（至少 24~48h）再定阈值。
**当前不动**，继续观察真实窗口。
