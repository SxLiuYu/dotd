# 实际解法（已落地，S2(b) 达成）

上面"下一步：硬拦 shell.run"**没有采用**。它不是好办法——判断"同类任务"要靠语义，
硬拦必然误伤"确实该用 shell 的活"。改从根因下手，效果更好且不误伤。

## 根因（不是模型不听话）

自造工具此前只是**注入到提示词里的一段文字**。模型要做的是：
「读到这段文字 → 自己意识到可以 invoke → 把工具名翻译成 `tool.invoke(name=<工具>)`」。
这是一次**间接映射**，对 deepseek / glm / agnes 三个厂商全部超纲。
所以三次提示词尝试全败，不是措辞问题，是**架构把难度丢给了模型**。

## 解法（代码约束，第 95-96 轮落地）

把自造工具**动态注册成独立 tool**：名字就是工具名、带自己的 `args_schema`。

- 暴露：`toolSpecs()` 里把动态工具并进工具表（`dynamicToolNames`，dot.ts L1700/L1714）
- 路由：模型照着调会撞 `unknown_tool`（工具未登记），所以在**派发口**翻译成
  `tool.invoke(name=<它>, args=<模型参数>)`（`isDynamicTool` L2013、`execTool` L2035）
- 治理不绕过：动态工具**不进** `config/tools.yml` 白名单，翻译后走 `tool.invoke`
  既有的 dangerous 档 + 每次执行审批，审计/日志/断点续跑都还在同一条路径上

顺带修掉一个真缺陷：日志里出现过
`{name:'word-count', args:{args:{text}, name:'word-count'}}`（双层包裹），
原因是注入措辞让模型以为要自己拼 `tool.invoke` 的参数；改掉措辞 + 加严格解包守卫。

## 结果

- `scripts/s2-reuse.sh`：模型发 `word-count` → 翻译成 `tool.invoke` → succeeded
- 跨模型：deepseek-v4.1-flash / glm-5.3-flash / agnes-3.0-flash **三个厂商全 PASS**
  （这三个此前全部失败）
- 更严判据复验（`scripts/s2b-verify.sh`，本会话）：不再"只要出现 tool.invoke 就算过"，
  改要求①有 tool.invoke ②**全程零 shell.run** ③工具数不变 ④任务 done 且有回答。
  **连跑 3 次全 PASS**，每次工具序列都是 `[tool.invoke:succeeded]`，工具数 2→2。

## 为什么这个解法优于"硬拦 shell.run"

| | 硬拦 shell.run | 动态注册 + 派发口翻译 |
|---|---|---|
| 要不要判断"同类任务" | 要（语义判断，必然误伤） | 不要（模型自己选工具，选错也能执行） |
| 该用 shell 的活 | 可能被卡死 | 完全不受影响 |
| 模型负担 | 仍要理解注入的文字 | 工具就在工具表里，和 `fs.read` 一样平铺 |
| 治理 | 需另开通道 | 复用 `tool.invoke` 的审批/审计 |
