# dotd 要对齐 Meta Muse 什么

> 写于 2026-10-20。
> 左列是**从 The Verge 16 篇报道里挖出来的 Muse 事实**（见 `meta-muse.md`），
> 右列是**我实际查过的 dotd 现状**（数据库 / 配置文件 / 代码）。
> 中间那一列是**差距**，最后一列是**要做什么**。

---

## 一句话结论

**Muse 的能力 dotd 大约有一半，形态几乎全缺。**

- **能力层**：文件、终端、浏览器、定时、跨站比价 —— dotd 都有，甚至更细（20 个工具 vs Muse 的 10 个）
- **形态层**：原生 App、可爱形象、主动打扰、可视操作、Stripe 付款 —— **dotd 基本是零**
- **最缺的一条**：**它不能主动找你**。dotd 现在只有你问它才答。

---

## 1. 能力对齐表

| Muse 能力 | dotd 现状 | 差距 | 怎么办 |
|---|---|---|---|
| **隔离 Linux 计算机**（浏览器/CPU/内存/存储）| ✅ **已有** `dotd-dot-dot1` 容器 | 无 | — |
| **浏览器操作** | ✅ `browser.open/act/snapshot/close` | 无 | — |
| **读文件 / 写文件 / 建目录** | ✅ `fs.read/write/list/stat/remove` | 无 | — |
| **跑命令**（bash/Python/Node/git）| ✅ `shell.run` | 无 | — |
| **定时任务** | ✅ `schedule.create/list/remove` + 5 条 cron | 无 | — |
| **网页抓取** | ✅ `net.get`（182 次实际调用）| Muse 反而**没有**通用 GET | dotd 这边更强 |
| **跨站比价 / 加购物车** | ⚠️ **技术上能做**，但没验证过 | 缺**实测** | 需要一次真实验收 |
| **填表单** | ⚠️ 同上 | 缺**实测** | 同上 |
| **读 Gmail** | ❌ **没有** | 要 OAuth + 邮件适配器 | 新建 `integrations/gmail` |
| **起草/发邮件** | ❌ **没有** | 同上，且要审批 | 同上 |
| **读日历 / 建事件** | ❌ **没有** | 要 OAuth + Calendar 适配器 | 新建 `integrations/calendar` |
| **接 Stripe 付款** | ⚠️ 有 `shop.checkout`（dangerous 档）| **没接过真 Stripe** | 要么接 Stripe，要么明确说不支持 |
| **打电话** | ❌ 没有（Muse 也没有）| 平手 | 不做 |
| **连第三方 SaaS**（Notion/GitHub/Figma…）| ✅ `mcp.call` | 缺**具体适配** | 逐个加 MCP server |

**小结**：Muse 的 6 个核心任务，dotd **能覆盖 4 个**（跟进、比价、买东西、联系服务商），
**缺口只在 Gmail / Calendar 这两个账号级集成**。

## 2. 形态对齐表（这里是真正的鸿沟）

| Muse 形态 | dotd 现状 | 差距 |
|---|---|---|
| **iOS / Android / Web / Mac / iPad 原生 App** | ❌ **只有飞书一个入口** | **最大差距** |
| **可爱形象（小熊），可起名** | ❌ 无 | 无形象层 |
| **主动 ping 你**（"it had been pinging me"）| ⚠️ 有 `schedule` 能定时，但**没有「主动发起对话」** | 缺主动打扰机制 |
| **操作过程可视**（盯着虚拟浏览器窗口）| ❌ 飞书里只有文字结果 | 缺过程可视化 |
| **在虚拟浏览器里填表单给你看** | ❌ 同上 | 同上 |
| **点头像看活动/回执** | ⚠️ 有 `starts/audit_log` 数据，**但没有产品界面** | 缺 UI |
| **审批屏**（金额/收件人/同意拒绝）| ⚠️ 有 `approvals` 表（120 条）+ `tier: dangerous` | **有后端没前端** |
| **Muse Charm 硬件** | ❌ 无 | 不追 |
| **眼镜** | ❌ 无 | 不追 |

## 3. 逐条差距的严重性

### 🔴 必须补（否则「能力对齐」不成立）

**1. Gmail 读 + 起草邮件**
- Muse 的招牌任务就是「跟进邮件」。
- dotd 完全没有邮件能力。
- 需要的：OAuth 流程 + Gmail API 适配器 + 发信前的审批。

**2. Calendar 读 + 建事件**
- 同上。Muse 能「发现日历、审核后建/改/删事件」。
- dotd 有 `schedule`（自己的 cron），但**不是你日历里的日程**。

**3. 主动发起对话**
- 这是 Muse 最核心的体验差异：「它上周一直在 ping 我」。
- dotd 现在**只能被动应答**。
- 技术上不难（`schedule` 已有），缺的是「允许 agent 主动发消息」这个开关和产品设计。

### 🟡 应该补（形态对齐的关键）

**4. 过程可视化**
- Muse 让你**看着它操作**（虚拟浏览器窗口）。
- dotd 在飞书里只给你最后一句。
- 最小可行：把 `browser.snapshot` 的截图回传 + 关键步骤播报。

**5. 审批界面**
- dotd 的 `approvals` 表有 120 条记录、`tier: dangerous` 分级 —— **后端是齐的**。
- 缺的是**飞书里的卡片式审批**（带金额、收件人、同意/拒绝按钮）。

**6. 活动/回执页**
- `audit_log` 3709 条、`steps` 8814 条 —— 数据都在。
- 缺一个「点头像看它干了什么」的入口。

### 🟢 可以不追

- **原生 App**：dotd 的定位是「在飞书里干活」，重做一个 App 等于重做产品。
- **可爱形象**：锦上添花，不影响能力。
- **硬件**：不追。
- **打电话**：Muse 自己也没有。

## 4. 如果只做三件事

按「能力对齐 + 形态对齐」的要求，性价比最高的三件：

| 优先级 | 做什么 | 为什么 | 工作量估计 |
|---|---|---|---|
| **P0** | **主动发起对话** | 这是 Muse 和 dotd 最本质的差别。没有它，dotd 只是「一个能调工具的聊天窗口」 | 中（`schedule` 已有，加「主动发消息」通道）|
| **P1** | **Gmail + Calendar 集成** | Muse 招牌任务的入口，dotd 零覆盖 | 大（OAuth + 两个适配器 + 审批）|
| **P2** | **过程可视化 + 审批卡片** | 后端全齐，只差飞书里那层 UI | 中（有 `approvals`/`steps`/`snapshot` 可直接用）|

## 5. 我建议先别做的

**别急着做原生 App。**
Muse 有 App 是因为它要卖给几十亿人；dotd 的入口是飞书，飞书本身就是 App。
**把飞书里的体验做厚，比另起一个 App 划算得多。**

**别急着做可爱形象。**
Muse 靠可爱降低防备，是因为它要收你的信用卡和 Gmail 密码。
dotd 的场景不一样，抄表层会长得别扭。

---

## 6. 需要你定的三件事

1. **「能力一致」是逐条对齐，还是覆盖它的核心场景就行？**
   逐条的话（Gmail / Calendar / Stripe / 8 个 SaaS）工作量是「核心场景」的 5 倍以上。

2. **「交互形态一致」是指什么？**
   - (a) 有 App（iOS/Android/桌面）—— 等于重做一个前端
   - (b) 有「主动找你 + 过程可视 + 审批屏」这套交互 —— 在飞书里能做
   - (c) 有可爱形象和拟人感 —— 视觉层

3. **Gmail / Calendar 要接真的吗？**
   接了就意味着要过 Google 的 OAuth 审核、要处理 token 加密存储、要写发信审批。
   也可以先做成「能读本地导出的邮件 / 能读 .ics 文件」。

## 7. 事实边界（别把我的判断当事实）

**确认的事实**（The Verge 报道 + 我查过的 dotd 现状）：
Muse 的多端、能力清单、集成列表、隐私争议；dotd 的 20 个工具、1248 任务、120 条审批。

**我的判断**（可能错）：
- 「Muse 能力 dotd 有一半」—— 这是我按任务清单逐条比的，不是量化测评
- 「主动对话是最本质的差别」—— 这是我的产品判断
- 工作量估计 —— 很粗，可能差一倍

**我不知道的**：
- Muse 的记忆机制、并行能力、失败重试、审批粒度（见 `meta-muse.md` 第 8 节）
- 你要的「一致」具体到什么程度
