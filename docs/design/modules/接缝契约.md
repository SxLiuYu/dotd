# 接缝契约（模块间一致性唯一仲裁文档）

> 属主：本文件由接缝仲裁员产出，是六模块文档（CP=control-plane、MR=model-router、
> GOV=governance、EX=execution、MEM=memory、SF=surfaces）之间**共享资源所有权、跨模块
> 接口签名、时序与术语**的唯一裁定。各模块文档与本契约冲突处，以本契约为准；模块修订
> 只需照 §8"待改清单"逐行执行，不再互相"提请仲裁"。CONTEXT.md（CT）优先级高于一切模块
> 文档与本契约。行号引用指各文件当前磁盘版本（均 rev2 系）。
>
> **口径声明**：各模块提交给本仲裁的"接缝诉求"摘要与磁盘 rev2 文本不一致时（多处），
> 一律以磁盘 rev2 文本为事实基准，摘要中的旧口径在下文逐条作废。

## 1. 数据库、迁移与表所有权

**D1 唯一库文件：`~/.dotd/dotd.db`（WSL 内 daemon 用户的 HOME 下）**
- 采纳：CP:32（§1.3）、MEM:63/54（§5.3/S1）、SF:6（数据目录 `~/.dotd/`）三方一致的 rev2 立场。
- 作废：GOV:33 的 `control.db`（O5 就此关闭；GOV 经 `DOTD_DB_PATH` 注入的机制保留，装配层
  统一指此路径）；CP 旧稿 `db/main.db`；MEM 摘要的 `~/dotd/dotd.db`（无点前缀旧口径）。
- 摘要"meta.schema_version 统一管迁移版本"作废——见 D3。

**D2 连接：全 daemon 共享一条 better-sqlite3 连接；`WAL + synchronous=FULL + busy_timeout=5000` 由启动者设一次**
- 冲突裁定：CP:58（"记忆模块自连用 NORMAL、每连接各设"）vs MEM:299/538（rev2 让步统一到
  FULL）vs SF:339/MEM:295（"所有循环共享同一连接"）。**以 MEM rev2 + SF 为准**：单连接下
  CP 的 per-module PRAGMA 差异不存在，synchronous=FULL（journal 与 messages 同级持久，
  CT:44 优先）。CP §2.1-2 相应句作废。
- `foreign_keys` 不全局 ON（MEM:302-306 论证成立）。
- **铁律：不建跨模块所有权的 FOREIGN KEY**（CP:34 采纳 MEM:376 实质约束；GOV §7 的同表内
  FK 如 `approvals→decisions` 属同属主，允许）。现存的越界声明全部降级为弱引用列：
  - SF:107 `surf_heartbeat_state.ct_id REFERENCES crontabs(id)`——整表作废（见 H1）；
  - SF:117 `surf_tg_card_state.approval_id REFERENCES approvals(id)`——去 REFERENCES，保留列；
  - EX:415/437/459 `exec_dots/exec_identities` 注释"与控制面 dots 表 FK"——**全系统没有
    dots 表**（六份 rev2 的 DDL 均未建 `dots`，CP:133/EX:415 只引用了它）。裁定：阶段一
    不建 dots 表，`tasks.dot_id`/`exec_dots.dot_id`/`mem_threads.dot_id` 一律 TEXT 弱引用，
    MVP 恒 `'dot1'`；dot 主档（配额、身份表等）列入阶段三设计项。
- WAL/busy 之外**不允许第二进程写库**（SF 时序契约与之一致；CLI 只走 HTTP）。

**D3 迁移版本：`PRAGMA user_version`，控制面 db 层为唯一 runner**
- 依据：CP:33 与 GOV:33/967 一致。各模块交付迁移包（CP 自有、GOV schema.sql、SF §4、
  MR `010_model_router.sql`、MEM §5.3、EX §9、以及本契约新要求的 `events`/`crontabs` 包），
  由 CP runner 按注册顺序执行、递增 user_version；失败→拒启动（CP:461、MEM §6.3 同级）。
- 不建 `meta` 表（CP 摘要 `meta.schema_version` 作废；CP §1.3 自身已采 user_version）。
  kv 状态自建表先例：`gov_seq`/`router_state`/`mem_maintenance_state`/`surf_sse_cursor`。

**D4 表所有权登记表（唯一权威，替代六方各自的声明）**

| 属主 | 表 |
|---|---|
| CP 控制面 | `tasks`、`task_results`、`steps`、`event_decisions`、`resource_events`、`events`、`crontabs`（后两张见 E1/H1） |

`mem_threads/mem_messages`，以磁盘为准。

## 2. 事件入口与任务队列（SF ↔ CP ↔ MR）

**E1 事件表唯一：`events`，归控制面；id = INTEGER AUTOINCREMENT**
- 收敛：SF rev2 §2.0/§13-5（"events 归 CP，本模块零写入"）与 CP 摘要（拥有 events）一致；
  **CP rev2 里"event_log/heartbeat_target/jsonl_offset 字段属主是 surfaces"（CP:25/36/590，
  引用 SF rev1 行号）作废**。SF 摘要里"本模块是 event_log/jsonl_offset/blobs 字段属主、
  event_log.id = SSE 游标"同样作废（SF rev2 §4.5 已自裁 SSE 游标=独立 `bus_seq`）。
- 最小 DDL（CP 迁移包落地，吸收 SF 字段级要求）：
  ```sql
  CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source TEXT NOT NULL CHECK (source IN ('http','file','heartbeat','telegram','email')),
    dot_id TEXT NOT NULL, actor TEXT NOT NULL,
    dedup_key TEXT UNIQUE,                       -- NULL 允许（多条 NULL 互不冲突）
    payload TEXT NOT NULL,                       -- JSON；业务扩展进 payload 不加列（SF C1）
    status TEXT NOT NULL DEFAULT 'pending'
      CHECK (status IN ('pending','matched','ignored','inbox')),
    received_at INTEGER NOT NULL
  );
  ```
- CP 侧改名：`tasks.source_event_log_id`→`source_event_id`；`event_decisions.event_log_id`→
  `event_id`；CP 全文"event_log"措辞→"events"。CP:401 写的 `status='enqueued'` 作废→
  `matched`；低置信待人工→`inbox`（与 SF:300 一致）。CP §8 接口清单缺 `ingestEvent`，
  必须补为唯一机器事件入口（`wakeIngest()` 并入其内部唤醒，不再单列）。
- `ingestEvent` 撞 `dedup_key UNIQUE` → 幂等返回 `{eventId, dup:true}`（旧事件 id），
  不重入管线（CP 摘要、SF:269/228 一致采纳）。
- SF 时序契约（摘要"<10ms 同步单事务，reject/dup 也必落审计行"）裁定：`ingestEvent` 的
  落库+规则匹配同步 <10ms、LLM 匹配异步（SF:339 两段式成立）；**从未抵达 CP 的拒绝**落
  `surf_ingress_rejects`（SF 自有表），抵达后的 dup 落 `events`——两套审计不混写。

**E2 投递接口签名（唯一）**
```ts
ControlPlane.ingestEvent(e:{source:'http'|'file'|'heartbeat'|'telegram'|'email'; dotId:string;
  actor:string; payload:unknown; dedupKey?:string; priority?:number})
  : { eventId:number; dup:boolean }
ControlPlane.submit(req:{title:string; goal:string; priority?:number; runAt?:number; dotId?:string;
  threadId?:string; payloadJson?:string; eventId?:number}): Task
```
- 术语作废：`submitEnvelope` / `Envelope` / `enqueue(env)`（CP 摘要与 CP:271/381/572/S6 引用
  的接口名）——SF:181 rev2 已宣告 Envelope 整体作废，此裁定生效。
- **GOV/SF 摘要称"事件适配器只做 normalize+dedup 后调 ingestEvent，不建任务不分类"**：与
  CP §6.1 一致——匹配分类在 CP，适配器只投递。`priority` 由适配器按 SF §5.1 映射表传入
  （interactive=1 / heartbeat·hook=5 / bulk=7），CP 不再自定档位。
- `submit.threadId?`：采纳 MEM:174（Q1 关闭）——对话任务由 SF 先 `memory.openThread` 再带
  threadId 提交；事件/心跳任务不带。
- `submit.payloadJson?`：采纳 MEM:219（Q1 关闭），落 `tasks.payload_json TEXT`（CP §3.1.1
  补列）；MEM 的 title 前缀编码过渡方案作废。
- dedup_key 规则以 **SF §4 表为唯一权威**：`hb:<ct_id>:<next_fire_ms>`、
  `file:<path>:<ino>:<gen>:<行号>`、`<source>:<extId|sha256(body)[0:16]>`、`tg:<update_id>`。
  CP 摘要旧式（`hb:<target>:<fireSeq>`、JSONL 缺 gen）作废。

**H1 心跳定时：单表 `crontabs`，归控制面；`heartbeat_target` 与 `surf_heartbeat_state` 作废**
- 三方冲突：CP rev2（heartbeat_target 归 surfaces，CP:266）vs SF rev2（crontabs 归 CP，
  SF:38/§5.4）vs CP 摘要（拥有 crontabs）。**裁定 SF rev2 + CP 摘要胜出**：
  ```sql
  CREATE TABLE crontabs (   -- CP 属主
    id TEXT PRIMARY KEY,                          -- 'ct_'+nanoid
    dot_id TEXT NOT NULL, title TEXT NOT NULL, prompt TEXT NOT NULL,
    cron TEXT NOT NULL, enabled INTEGER NOT NULL DEFAULT 1,
    next_fire INTEGER NOT NULL, last_fired_at INTEGER,
    last_fire_seq INTEGER NOT NULL DEFAULT 0,
    last_fire_status TEXT,                        -- fired|skipped_quiet|skipped_busy|error
    skip_if_busy INTEGER NOT NULL DEFAULT 1, quiet_hours TEXT,
    catchup TEXT NOT NULL DEFAULT 'latest' CHECK (catchup IN ('latest','skip'))
  );
  ```
  （原 surf_heartbeat_state 行为扩展列并入，SF Q9 裁定为"并入"——单表免 JOIN，
  references D2 弱引用铁律也免一条 FK。）
- 分工：表的读写与"何时投递"判定循环 = **CP scheduler 内注册的 `heartbeat.tick` 任务**
  （tick 算法语义采信 SF §5.4 rev2 版：先推进 next_fire 后投递、quiet_hours、skip_if_busy、
  catchup='latest' 补投一次）；触发 = `cp.ingestEvent(source='heartbeat',
  dedupKey='hb:<ct_id>:<next_fire>')`。CP §4.3 的"fire_seq 自增防重"作废（next_fire 时间戳
  天然唯一）。CP:266 "自建 crontabs 删除"整段按本节改写；CP 摘要"crontabs 归控制面"生效。
- `skip_if_busy` 数据源 = `cp.list({status:['queued','running'],dotId}).length`（SF:262）。

**H2 HTTP 监听唯一 = `127.0.0.1:7788`（SF 属主）；CP 的 8642 作废**
- 裁定采纳 SF:49/Q0：全 daemon 只有一个 HTTP 监听（鉴权/CORS/SSE/CLI base 单点，
  SF §5.2/§5.6）。CP:50/572/596 的 `:8642` 及摘要"HTTP 绑 8642"作废——CP 的 REST 子集
  （GET /tasks、GET /journal/:taskId、GET /guard 等）由 SF 路由器**进程内转调 CP 函数**，
  不亦不开第二监听；路径前缀并入 SF 的 `/api/*` 命名空间。CP §12/§8"Web UI 审批卡片数据源
  = GET /journal/:taskId + GET /tasks"改为"经 SF /api/* 转调同名 CP 函数"。

## 3. 步骤身份、journal 与幂等（CP ↔ EX ↔ GOV ↔ MR）

**J1 步身份统一 = `call_id`（TEXT ULID），并补齐 LLM 步**
- 五方一致（CP:105/370、GOV S1/438、EX S1/478、MR:209、SF C4）：`steps.call_id` ==
  治理 `ToolCall.callId`/`approvals.journal_step` == `exec_calls.call_id` ==
  `model_call_log.attempt_id`。内部 `(task_id,seq)` 不外泄（CP:371）。
- **缺口裁定（本契约新裁决）**：MR 要求 `attemptId == journal 步骤 id`，但 CP `beginLlm`
  不生成 id（CP:320/539 只返回 seq）。裁定：`journal.beginLlm(taskId,epoch,promptDigest)`
  返回 `{seq, callId}`，`steps.call_id` 对 llm 步同样填写（`uq_steps_call` 已覆盖）。
  主循环 LLM 调用的 `attemptId` = 该 callId。**非 journal 上下文的模型调用**（CP 事件匹配、
  GOV precheck/postReview、MEM 摘要投递的即时调用）`attemptId = 'nonj:'+ULID`——MR 接受任意
  TEXT，仅作 `model_call_log` 聚合键，同一次逻辑调用重试时不变。MR §6.2 补一句此约定。
- `RouteMeta.attemptSeq` 所有权维持 MR §6.2 裁决（路由内自增，调用方不传）。
- 重放 call_id 规则消歧（两条路径，不混淆）：
  1. **已派发过 exec 的孤儿步**（started 孤儿 / `exec.call.interrupted` 回报）→ 重派必用
     **新 call_id**（CP S1/580、EX S1/560"重派换新 call_id 属 journal 决定"）。
  2. **审批挂起从未派发过的步**（pending）→ 批准后**复用原 call_id** 执行（从未触 exec、
     ledger 无记录，无幂等冲突；GOV §3.1 活动单重入返回同单/claimAndAllow 依赖此）。
- 治理终态单重放禁令维持（GOV §3.1：终态步重入→deny+审计，控制面不得重放终态步）。

**J2 副作用词表落执行面能力目录（补齐 CP S1 与 EX 的接口空洞）**
- EX `Capability`（EX §5.2/§10）**增字段 `sideEffect:'safe'|'replayable'|'unknown'`**；
  未声明按 `unknown` 安全默认（CP:85/S1）。这是 journal 崩溃恢复分流的唯一依据（CP §5.1）。
- 治理 `tools.yml` 仍只登记 `name+tier`（GOV §2.2）；tier 与 sideEffect 是两套正交词表。
  启动校验：`getCapabilities()` 词表 ⊆ tools.yml 登记名，未登记即 deny（GOV S2）；
  增删工具 bump `runtime_ver`（EX S2）。
- CP §8/S1 的 `toolRegistry[step.name].sideEffect`（CP:657）改为从
  `exec.getCapabilities(dotId)` 的缓存读取，CP 不维护第二注册表。

**J3 journal 接口名（GOV 引用面统一到 CP 定义）**
- 唯一写路径接口 = CP §8：`beginTool→endTool / markPending / beginLlm→endLlm /
  getStepByCallId / reconcileAndResolve / tail`。GOV §8.2 伪码与主循环序里的
  `journal.beginStep/endStep` 改名为 `beginTool/endTool`。
- **新增**：`journal.skipStep(callId, reason)`——承接 GOV §8.2"deny/ok=false 由控制面把步
  标 skipped"的义务（CP 接口现缺此方法，必须补）。
- 工具全量参数/结果只进 `steps`（>32KB 走 blob）；`mem_messages` 同 kind 只存 digest+200
  字符预览——CP:320/MEM S6/GOV"参数 sanitize 后入库"三方一致，双写禁令成立。
- 恢复顺序固定：先问 journal（要不要重放）再问 messages（聊到哪）（MEM S6 = CP §7.3）；
  LLM 恢复全文由记忆负责（MEM content 全文），CP:492 接缝成立。

**J4 周期任务唯一宿主 = `ControlPlane.registerInternalJob(spec)`**
- 全部 cron 走 CP scheduler 单点（CP §8/S4/R7 胜出）：GOV `expirePending`/`compactAudit`/
  提醒扫描；MR `pool.probe.*`(30min)/`recon.scan`(6h)/`breaker.probe_timer`(1min)/
  `router.janitor`(每日)；CP `queue.gc`；H1 `heartbeat.tick`；MEM `memory-compaction`
  (每小时探测)/`memory-retention`(每日)。**摘要里 MEM S10"注册进心跳调度器"即此口**；
  MEM 的两个 job 本体只做探测与投递（重活经 `submit` 入队、track=light），不是模型直调。
- SF §5.4 的 `registerIntervalJob(name,ms,fn)` **作废**——SF 只声明 heartbeat.tick 的
  算法语义供 CP 实现；`kind:'light'` job 在 throttled/halted 时跳轮（CP S4），heavy 照跑。

**J5 容器配额与水位指令（CP ↔ EX 分工定案）**
- 数值冲突裁定：CP 声明 `--memory=2g --cpus=2`，EX 默认 1536MB/2000m。**实施值归 EX**
  （`exec_dots.limits_json` 是配额唯一事实源，默认 memMb=1536、cpuMillis=2000）；CP 只经
  EX API 消费，不硬编码数字。CP §6.4"每容器 --memory=2g --cpus=2"改述为"配额值以
  exec_dots.limits_json 为准（默认 1536m/2c）"。
- 指令映射（CP S2 要的 `Sandbox.pause/unpause/resume/kill/stats`）：
  - pause/unpause → **EX 新增** `pauseContainer(dotId)` / `unpauseContainer(dotId)`
    （docker pause/unpause；EX 现有 suspendDot/resumeDot 语义相同，统一用
    suspend/resume 命名亦可，但必须暴露幂等 unpause 路径供 CP 解冻循环）；
  - kill → `destroyDotContainer(dotId,{keepVolumes:true})`；
  - stats → **EX 新增** `getContainerStats(dotId): {memMb, hasInflightCall}`；
    `hasInflightCall` 判据 = `exec_calls.state IN ('sent','running')` 存在行（EX 表内事实）。
- **`docker stats` 轮询执行者裁定**：CP §2.1"唯一的 child_process 是 docker stats"与
  EX §2.1-1"不写 docker CLI 子进程"矛盾——**归 EX**：getContainerStats 内部用 dockerode
  stats API（daemon 同进程 unix socket），CP 只按周期调用。CP 拓扑图中"唯一 child_process"
  一句作废（pause/unpause/kill 同样经 dockerode，非子进程）。
- 水位阈值数字（CP §6.3 32GB/.wslconfig/兜底线）属 CP 内部+待主人标定（CP 开放问题 #3），
  无跨模块冲突，不裁。

**J6 审批联动钩子（GOV ↔ CP，签名定案）**
- 唯一审批事实源 = GOV `approvals`（GOV §0.1、CP S3、SF §2.0 三方一致）。不存在第二条
  审批流水；`deliver_state` 机制彻底作废（GOV §0.1 投影表随 SF rev2 删表而失效——SF 已
  自废，只保留 `surf_tg_card_state` 通道侧事实）。
- 钩子签名（统一，含两处修正）：
  ```ts
  // CP 导出，治理/Runner 调用：
  setAwaitingApproval(taskId, epoch, approvalId): void;
  onApprovalSettled(taskId, approvalId, ok:boolean,
                    meta?: {note?:string; revoke?:string}): void;
  ```
  - GOV `GovDeps.controlPlane.setAwaitingApproval(taskId, approvalId)` 缺 epoch——**以 CP
    为准**；实际调用方改为 **Runner**（CP §12 骨架 CP:662 本就是 Runner 调），治理在
    evaluate 返回 approve 后**不再直接调它**（治理不持有 epoch）。GOV §8.2/§9-S6 相应改写：
    治理只负责 `onApprovalSettled`（decide 提交、expirePending 提交、revoke 抢先——三条
    异步路径在调用栈内触发）。
  - `onApprovalSettled` 增 `meta{note,revoke}`——**以 GOV 为准**（CP:555 无 meta 的签名作废），

## 8. 一条事件的端到端时序（全链路定稿）

```
①外部事件 → SF ingest 入口（鉴权/zod/限流）
② cp.ingestEvent({source,payload,dedupKey,priority}) —— 同步单事务：INSERT events
   （撞 dedup UNIQUE → 返回旧 eventId,dup）+ setImmediate(scheduler.wake)
③ CP 匹配（规则层→LLM 层 complete({track:'light',deadlineMs:15000,attemptId:'nonj:…'})，
   light_events 前缀表含 event.match）：
   BEGIN IMMEDIATE { INSERT tasks(id='tk_ev_'+events.id, source_event_id, thread_id=NULL)
                    + INSERT event_decisions + UPDATE events.status='matched' }  —— 同事务防双建
④ pop（背压门控 + maxRunning + run_epoch+1）→ Runner 协程领任务
⑤ Runner：memory.openThread('event')/或对话任务已带 threadId → cp.bindSession(taskId,epoch,
   {sessionId:threadId,threadId}) → memory.buildContextBundle(经 /fs/ops 读 /dot/home)
⑥ 每步：journal.beginLlm→callId→modelRouter.complete({track:'primary',attemptId:callId})→endLlm
⑦ 工具步：journal.beginTool(→callId, status='started'=call_sent)
   → governance.evaluate(ctx{epoch 经 taskRef}, call{callId,tool,params,identity})
     ├ allow/review_pass → exec.runTool(ToolCall{call_id=callId, dot_id, identity, deadline_ms})
     │      ledger 幂等同 call_id 至多一次；endTool(=call_done) 落库才派下一步
     ├ deny → journal.skipStep(callId) → 任务改道/失败（终态收口调 sealTask）
     └ approve → journal.markPending(步转'pending') + cp.setAwaitingApproval(taskId,epoch,apId)
        → 任务 awaiting_approval，Runner 让位（不占 runningCount）
⑧ SF 卡片/通知（approval:created → SSE + renderTgNotice）；web/TG/CLI 回复 → gov.decide()
   （条件 UPDATE 先到先得；迟到 → ok:false+late_decision 审计）
⑨ decide 事务提交 → hooks.onApprovalSettled(taskId,apId,ok,{note}) → CP：ok→queued
   (resume_from_seq=该步, priority≤2) / deny·expired→该步 skipped 继续改道
   —— 恢复执行一律 claim() 后按 final_params_json+note，以同 callId 步 pending→started
   （新 epoch），从未派发过 exec，无幂等冲突（J1-2）
⑩ 结果回报：assistant 全文 appendMessage 入 thread（tool 消息只 digest+预览，S6 双写禁令）
⑪ 任务终态 → memory.sealTask（三种 outcome 全走）→ cp.finish(ok|err, epoch)
⑫ 崩溃穿插：unknown started 孤儿 → exec.reconcileCall(callId)（done 补记 / aborted 重放 /
   未知→journal.forceApproval(kind=side_effect_unknown, subject_key='unk:'+callId)）；
   exec 回报只 `exec.call.interrupted(callId)`，重派必换新 callId（J1-1）
```
模型故障支线：complete 抛 AllEndpointsDownError → CP `pauseByReason(taskId,'circuit_open')`
（= 挂起，无 waiting_model 态）→ MR 发 router.mode_changed + 求救（账本先行→deliver 经
SF NotificationChannels→兜底 append ~/.dotd/OUTBOX.md）→ mode 变好 → CP 批量回 queued
+ MR 恢复通报。
